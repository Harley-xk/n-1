# AI 工作规则 —— 测试策略

> 优先级仅次于 [base.md](base.md)。本规则回答「什么时候写测试、写在哪一层、写到什么程度」。
> 「`*.spec.ts` 与源码同目录」是**位置约定**，不是「每个源码文件必须配一个 spec」的覆盖率要求。

## 1. 核心原则：风险驱动，不按文件结构驱动

1. 测试的存在理由是**守护风险**，不是凑结构：逐文件配 spec 是仪式性负担，且给人「覆盖完备」的错觉（覆盖的是行数，不是风险）
2. 每个用例应能回答「**它防的是哪个未来错误**」；答不上来的用例应当删除
3. 类型系统能保证的（字段赋值、参数传递形态）不重复用单测守护

## 2. 单元测试取舍（按代码形态分级）

| 代码形态 | 例子 | 策略 |
| --- | --- | --- |
| 有分支 / 边界条件 / 易错逻辑 | 递归与循环引用、状态转换、日期处理 | **重点测**，优先覆盖边界与异常路径 |
| 契约守护类断言 | 「A 必须先于 B 判断」「敏感信息不得泄漏」 | **必测**——防的是未来改坏，价值最高 |
| 逻辑直白的纯函数 | 简单映射、格式化、取值转换 | 少量冒烟用例，或不写 |
| 纯赋值 / 构造传参 | 数据类、DTO、简单值对象 | **不写**（类型系统已守护） |
| 纯类型 / 接口 / 常量 | `interface`、`type`、枚举定义 | **不写**（无运行时行为） |
| Controller 薄壳 | 仅透传 Service 的方法 | **不写单测**，交由 e2e 验证真链路 |

## 3. 横切设施：高密度要求

`server/src/common/`（拦截器、过滤器、守卫、管道、工具函数）与 `web/src/api/` 等横切设施是框架底座，被所有业务模块依赖，**分支覆盖要求高**：

1. 全部分支（含防御性兜底分支）均需用例覆盖
2. 这类代码的分支细粒度 e2e 难以触达（如未知异常 500 路径），单测是主要守护层
3. 修改横切设施时必须先跑全量 `pnpm check`，而不是只跑相关用例

## 4. e2e 的职责边界

1. **后端 e2e（`server/test/`）**：验证装配与 HTTP 语义（路由可达、状态码、统一响应结构、模块注册），**不重复**单测的细粒度断言
2. **浏览器 e2e（`e2e/`）**：用户视角的页面交互验收；依赖后端就绪的用例在探测失败时自动跳过
3. 仅测试需要的临时控制器 / DTO 可在测试文件内定义，**不得**为测试在 `src/` 中添加演示端点（业务代码零污染）

## 5. 测试自身的规范

1. 用例名用**中文描述行为**（「应将 201 状态码归一为 200」），不照抄函数名
2. mock 只 mock **边界**（`ExecutionContext`、HTTP 层、数据库连接），不 mock 被测对象的内部实现
3. 测试文件豁免头部注释（见 [base.md](base.md) 第 1 节）
4. 删除源码时同步删除其 spec；重构使用例失去守护对象时**删除**该用例，而不是改写成形式化断言保绿
5. **测试符号一律显式导入**：server 端从 `@jest/globals` 导入（`describe` / `it` / `expect` / `jest` 等，`@jest/globals` 已在 devDependencies），web 端从 `vitest` 导入——不依赖 tsconfig 的全局类型注入，避免 IDE 对 spec 文件的项目归属歧义（`tsconfig.build.json` 排除了 spec，全局符号在错误归属下解析失败）；pnpm 严格依赖隔离下也不得 import 未显式声明的包
