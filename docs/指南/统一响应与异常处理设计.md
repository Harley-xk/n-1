# 统一响应与异常处理设计

> 本文约定 n-1 全部 HTTP 接口的响应结构与异常处理机制，是前后端共同遵守的**数据交换契约**。业务模块开发前请先阅读本文。

## 1. 需求背景

框架底座在未约定统一响应结构时，会随业务膨胀暴露四类问题：

1. **响应形态不一致**：各接口自行决定返回结构，前端无法用单一判定收敛「成功 / 失败」逻辑，每接一个接口都要写一遍判断
2. **异常信息裸奔**：框架级异常以英文消息甚至堆栈细节直接返回客户端，既不友好也不安全
3. **时间格式漂移**：各接口时间字段混用 ISO 字符串、本地时间字符串等形式，服务器与客户端时区不一致时产生隐蔽 bug
4. **成功失败语义模糊**：HTTP 状态码、业务状态没有明确分工，前端判定口径不统一

本设计以三个横切设施一次性解决上述问题：**响应包装拦截器**（成功路径）、**全局异常过滤器**（失败路径）、**业务异常类**（业务代码表达失败的标准方式）。

## 2. 方案设计

### 2.1 统一响应结构

所有接口的最终响应体形态（`server/src/common/interfaces/api-response.interface.ts`）：

```typescript
export interface ApiResponse<T = unknown> {
  /** 业务状态码：>=0 成功（默认 0，预留正数扩展位）；<0 业务错误（默认 -1，预留负数扩展位） */
  code: number
  /** 提示信息：错误时必有；成功时省略（JSON 序列化自动丢弃 undefined） */
  message?: string
  /** 业务数据：成功时为接口返回值；业务错误时可携带补充数据 */
  data?: T
}
```

成功响应示例：

```json
{ "code": 0, "data": { "name": "n-1 API", "version": "0.1.0" } }
```

错误响应示例：

```json
{ "code": -1, "message": "未找到该货币的汇率信息" }
```

### 2.2 错误码体系

错误码按**符号分段**，不使用枚举表：

| code 取值 | 含义 | 说明 |
| --- | --- | --- |
| `0`（默认） | 成功 | 预留正数扩展位（如「部分成功」等未来业务状态） |
| `-1`（默认） | 业务错误 | 预留负数扩展位（如 `-1001` 等细分业务错误码） |
| HTTP 状态码数值 | 框架级错误参考标识 | 仅出现在 HTTP 4xx/5xx 响应中，见 2.5 节 |

**判定约定（前端必须遵守）**：

- 成功 / 失败的**第一道判定永远是 HTTP 状态码**（2xx 即成功路径，4xx/5xx 即失败路径）
- 成功路径中再以**符号比较**判定业务状态：`code >= 0` 放行，`code < 0` 按失败处理
- **任何地方都不要写死 `code == 0` 或 `code == -1`**——具体数值属于实现细节，符号语义才是契约

> 为什么框架级错误的 code 是 HTTP 状态码数值（如 404）却仍属「失败」？因为此类响应必伴随 HTTP 4xx/5xx，在第一道判定中已归入失败；code 在此仅为参考标识（便于日志排查区分 404/401/400），不参与成功判定，与「`>=0` 成功」的符号语义并不冲突——符号语义只约束成功响应路径。

### 2.3 业务异常 BusinessError

业务流程中**可预期、需要以友好信息反馈给前端**的失败，统一抛 `BusinessError`（`server/src/common/exceptions/business-error.ts`）：

```typescript
// Service / Controller 中的标准用法
throw businessError('未找到该货币的汇率信息')

// 携带补充数据（如批量导入的逐行错误明细）
throw businessError('上传失败', { data: errors })

// 自定义 HTTP 状态码（默认 400）
throw businessError('汇率必须为正数', { status: 422 })
```

类定义要点：

- 继承 `Error`：保留真实堆栈供服务端日志定位抛出点
- 字段：`status`（HTTP 状态码，默认 400）、`code`（业务错误码，默认 -1）、`data`（附带数据，可选）
- 日常代码用工厂函数 `businessError()`，`new BusinessError()` 用于需要更精细控制的场景

**何时用 BusinessError，何时用 Nest 内置异常**：

| 场景 | 抛出方式 | 响应形态 |
| --- | --- | --- |
| 业务规则不满足（查无记录、状态冲突等） | `businessError('中文消息')` | HTTP 400，`code: -1` |
| 鉴权失败 | `UnauthorizedException` | HTTP 401，`code: 401` |
| 权限不足 | `ForbiddenException` | HTTP 403，`code: 403` |
| 资源不存在（RESTful 语义） | `NotFoundException` | HTTP 404，`code: 404` |

### 2.4 响应包装拦截器 TransformInterceptor

`server/src/common/interceptors/transform.interceptor.ts`，全局拦截器，处理**成功路径**：

1. **时间转换**：业务数据中的 `Date` 实例深度转换为毫秒 Unix 时间戳（见 2.6 节）
2. **状态码归一**：201 统一转 200（POST 创建接口不再产生 201），前端「HTTP 2xx 即成功」的判定保持简单
3. **包装**：`return { code, data: 转换后的数据 }`（成功时 `message` 为 undefined，序列化后自动省略）
4. **文件流直通**：`StreamableFile`（文件下载）跳过包装原样返回

Controller 因此**只返回裸业务数据**，不手动包装：

```typescript
@Get('exchange-rate/:currency')
async getRate(@Param('currency') currency: string): Promise<ExchangeRate> {
  const rate = await this.service.find(currency)
  if (!rate)
    throw businessError('未找到该货币的汇率信息')
  return rate   // 拦截器自动包装为 { code: 0, data: rate }
}
```

### 2.5 全局异常过滤器 HttpExceptionFilter

`server/src/common/filters/http-exception.filter.ts`，`@Catch()` 全捕获过滤器，处理**失败路径**，把一切未捕获异常归一化为统一结构。三个分支的**判断顺序是正确性核心**：

| 顺序 | 分支 | HTTP status | code | message | data |
| --- | --- | --- | --- | --- | --- |
| 1 | `instanceof HttpException` | `getStatus()` | = status | DTO 校验失败时 message 为字符串数组，`join(',')` 拼接为一行；否则取异常消息 | — |
| 2 | `instanceof BusinessError` | `exception.status` | `exception.code` | 自定义中文消息 | `exception.data` |
| 3 | `instanceof Error`（未知异常兜底） | 500 | -1 | 固定「服务器内部错误」 | — |

> **为什么 BusinessError 分支必须先于 Error 分支**：`BusinessError` 继承自 `Error`，若顺序写反，业务错误会被兜底分支吞掉，全部变成 500「服务器内部错误」。该顺序由单元测试与 e2e 测试共同守护。

未知异常（数据库连接失败、代码 bug 等）的原始消息与堆栈**只写入服务端日志**（Nest `Logger`），客户端仅收到中文化的兜底提示——既不泄漏内部实现细节，也保留了服务端的完整排查信息。

### 2.6 时间格式约定

前后端交换的时间字段统一使用**毫秒 Unix 时间戳**（`number`）：

- 时间戳本身无时区语义，从根上规避服务器 / 客户端时区不一致问题；双方各自按需转换展示（前端 `new Date(ts)` 即得本地时间）
- **Service 层直接返回 `Date` 实例**（不自行 `toISOString()` 或格式化字符串），序列化职责统一交给响应拦截器——`app.service.ts` 的 `getHealth()` 返回 `{ status, timestamp: Date }` 是该约定的标准样例
- 转换实现是拦截器内的纯函数 `serializeDates`（`server/src/common/utils/serialize-dates.ts`）：O(N) 单遍递归，按 V8 自适应优化友好的形态编写（固定分支顺序、`Object.keys` 遍历、原生 `map` 处理数组），典型响应的转换开销为微秒级
- **刻意不改写 `Date.prototype.toJSON`**：那是进程级原型污染，会影响日志、Swagger 生成与第三方库的内部序列化行为；显式转换的作用边界精确限定在「HTTP 响应序列化」这一层
- 请求方向（前端 → 后端）同样约定传毫秒时间戳，DTO 中的转换（时间戳 → `Date`）由各业务模块按需处理

### 2.7 注册方式

过滤器与拦截器以 `APP_FILTER` / `APP_INTERCEPTOR` 令牌注册在 `AppModule` 的 providers 中（而非 `main.ts` 的 `useGlobalFilters` 实例注册）：

```typescript
providers: [
  { provide: APP_FILTER, useClass: HttpExceptionFilter },
  { provide: APP_INTERCEPTOR, useClass: TransformInterceptor },
  // ...
]
```

收益：模块级注册使 e2e 测试（`Test.createTestingModule({ imports: [AppModule] })`）**自动继承**全局设施，无需在测试中手动复制装配；过滤器 / 拦截器未来需要注入依赖（如 ConfigService）时也天然支持。

### 2.8 前端消费约定

`web/src/api/http.ts` 的 axios 响应拦截器统一处理：

- **成功分支**（HTTP 2xx）：`code < 0` 时按失败处理（防御性兜底，符号判定）；否则 `return response.data`——**返回包装结构本身**
- **错误分支**（HTTP 非 2xx）：取 `error.response.data.message` 弹 `ElMessage.error` 统一提示，无响应（网络中断 / 超时）时提示「网络异常，请稍后重试」
- 文件流（`responseType === 'blob'`）跳过统一处理

**「返回包装结构」的关键原理（字段同名对齐）**：响应拦截器 `return response.data` 后，Promise resolve 的值是 `ApiResponse` 对象；axios 的类型系统认为它是 `AxiosResponse<T>`。两个结构的负载数据字段**恰好同名**（`ApiResponse.data` 与 `AxiosResponse.data`），因此调用方的既有习惯写法完全不变：

```typescript
// 泛型 T 的语义 = 业务数据类型（不是包装结构！）
const { data } = await http.get<{ status: string }>('/health')
// data 即业务数据本身，类型与运行时两层同时正确
```

这条「`http.get<T>` 的 `T` 填业务数据类型、解构 `data` 得业务数据」的约定是前端调用接口的标准姿势，**不要**再多解一层包装。若未来响应字段改名，`http.ts` 中的类型断言处是唯一需要同步的点。

## 3. 接口约定

五类场景的完整报文样例（均为真实链路的最终形态）：

**① 成功（含时间字段）**——`GET /api/health`：

```json
{ "code": 0, "data": { "status": "ok", "timestamp": 1757462400000 } }
```

**② 业务错误**——Service 抛 `businessError('未找到该货币的汇率信息')`：

```json
HTTP 400
{ "code": -1, "message": "未找到该货币的汇率信息" }
```

**③ 业务错误携带数据**——`businessError('上传失败', { data: errors })`：

```json
HTTP 400
{ "code": -1, "message": "上传失败", "data": [{ "row": 3, "error": "汇率必须为正数" }] }
```

**④ 框架级错误**——路由不存在 / DTO 校验失败：

```json
HTTP 404
{ "code": 404, "message": "Cannot GET /api/not-exist" }

HTTP 400
{ "code": 400, "message": "name should not be empty,name must be a string" }
```

**⑤ 未知异常兜底**——服务端代码抛出未预期的 `Error`：

```json
HTTP 500
{ "code": -1, "message": "服务器内部错误" }
```

## 4. 边界与异常

1. **Swagger 文档展示的是解包前类型**：`@nestjs/swagger` 依据 Controller 返回类型生成文档，展示的是 `data` 字段的类型，不体现包装结构（Swagger 路由经底层 HTTP adapter 注册，不经过 Nest 拦截器管道，`/api-docs` 本身也不会被包装）——使用 Swagger 时请自行脑补外层 `{ code, data }`
2. **文件下载直通**：`StreamableFile` 响应不包装（后端拦截器直通、前端 blob 跳过），两端均已预留
3. **无 body 状态码**：204/304 等语义上无响应体，与 `res.json()` 冲突；约定无数据接口返回 `null` 且状态码 200，如未来确需 204/304 再在拦截器加直通分支
4. **前端双重提示**：错误时拦截器统一弹 `ElMessage.error`，页面 catch 块若也弹提示会出现两条（如 HomeView 的兜底提示）。当前可接受；页面需要自定义错误处理时，在 catch 中识别拦截器已提示的错误并静默即可
5. **时间转换仅覆盖 HTTP 响应路径**：日志、消息队列、WebSocket 等其他序列化通道不受影响，如未来接入需按各自通道另行约定

## 5. 验收标准

1. 所有 HTTP 接口（含框架级 404、校验失败）响应体均为 `{ code, message?, data? }` 结构
2. 业务代码通过 `throw businessError('消息')` 表达业务失败，客户端收到 HTTP 400 与中文消息；未知异常不泄漏内部细节
3. 响应中的时间字段一律为毫秒 Unix 时间戳（number）
4. 前端以「HTTP 状态码 + code 符号」判定成功失败，不写死具体数值
5. 单元测试覆盖过滤器三分支、拦截器包装与时间转换、`serializeDates` 纯函数；后端 e2e 覆盖成功路径、404、BusinessError、DTO 校验四条真链路
6. 根目录 `pnpm check` 全绿
