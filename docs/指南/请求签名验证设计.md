# 请求签名验证设计

> 本文约定 n-1 的**写方法请求签名验证机制**：签名算法、请求头契约、豁免与自定义方案扩展模型、防重放设计与前后端接入方式。涉及对外接口（开放 API、第三方回调等）开发前请先阅读本文。

## 1. 需求背景

### 1.1 要解决的问题

框架底座若无请求防伪设施，写接口（POST/PUT/PATCH/DELETE）会暴露在三类风险下：

1. **脚本直刷**：任何知道 URL 的脚本都能绕过前端页面直接调用写接口（批量注册、灌数据、触发动作）
2. **参数篡改**：请求在客户端到服务端的链路上被中间人改写参数（代理、抓包重发）
3. **请求重放**：截获一次合法请求后原样重发（重复提交、重复触发动作）

请求签名机制让每个写请求携带「用约定密钥对请求关键要素计算的消息认证码」，服务端逐请求校验——签名不匹配（来源未知、被篡改）或时间窗外/已使用的请求一律拒绝。

### 1.2 机制定位与安全边界

**诚实声明：这是轻量防伪层，不是身份认证，也不防「合法客户端的恶意调用」。**

- 前端密钥随构建产物下发，**技术上可被提取**——本机制的对手是「不知道密钥的脚本与链路篡改者」，不是拿到密钥的调用方
- 身份认证（谁在调用）、权限控制（能调什么）由未来的鉴权体系承担，与本机制正交
- 签名头与鉴权头（如未来的 `Authorization`）互不干扰，可叠加使用

## 2. 方案设计

### 2.1 总体架构与请求链路

```text
浏览器/调用方                                server（NestJS 11）
┌──────────────────────┐    HTTP 写请求     ┌─────────────────────────────────────────┐
│ axios 拦截器自动签名   │ ───────────────→ │ rawBody 缓存（Nest 原生 rawBody: true）    │
│ （http.ts 请求拦截器） │   三件套头 + 原文体 │   ↓                                     │
│                      │                   │ SignatureGuard（APP_GUARD 全局守卫）       │
│ signRequest()        │                   │   开关 → 豁免 → 写方法判断 → 方案分发       │
│ （非 axios 场景手动签） │                   │   ↓ standard 方案：取头 → 时间窗 → 防重放  │
└──────────────────────┘                   │     → body 判定 → HMAC 比对               │
                                           │   ↓                                     │
                                           │ ValidationPipe → Controller → Service    │
                                           └─────────────────────────────────────────┘
```

- Guard 经 `APP_GUARD` 令牌注册在 AppModule（与 `APP_FILTER`/`APP_INTERCEPTOR` 同模式），e2e 测试自动继承
- Guard 先于 ValidationPipe 执行（Nest 请求生命周期：middleware → guards → interceptors → pipes → handler），非法请求不会进入参数校验

### 2.2 签名算法与签名串定义

**算法：HMAC-SHA256**（密钥作为 MAC 密钥参与运算，不拼进签名串——免疫长度扩展攻击，密钥不出现在任何待签数据中）。

```text
signString = [method, path, body, timestamp, nonce].join('\n')
sign        = HMAC-SHA256(signString, secret)   // 输出小写 hex
```

| 段 | 取值 | 说明 |
| --- | --- | --- |
| `method` | 请求方法大写（如 `POST`） | 防同一 path 的签名跨方法挪用 |
| `path` | 含 `/api` 前缀的 pathname | 不含 query、不含 origin、保留 URL 编码原样 |
| `body` | 原始请求体字符串 | 判定规则见下表；空 body 也占位，**段数恒为 5** |
| `timestamp` | 毫秒 Unix 时间戳字符串 | 与全仓时间约定一致 |
| `nonce` | 一次性随机串 | 每次请求重新生成 |

分隔符用 `\n`：method/timestamp/nonce 的字符集不含换行；path 中换行只会以编码字面量 `%0A` 出现；body 是 `JSON.stringify` 产物，控制字符一律转义为 `\\n` 字面量——**段内不会出现真实换行，`\n` 作分隔符无拼接歧义**（避免 `path=/a,body=bc` 与 `path=/ab,body=c` 签名串相同的问题）。

**body 段判定规则**（绑原始字节，标准方案限定 JSON API，fail-closed）：

| 请求形态 | body 段取值 |
| --- | --- |
| JSON 带体（content-type 含 `application/json`，rawBody 存在） | `rawBody.toString('utf8')` |
| 无 body 写请求（无 content-type 或 Content-Length 为 0，如纯动作型 POST「提交/触发」） | 空串（合法场景） |
| 非 JSON content-type 且实际带体（form/XML/multipart） | **401 拒绝**——标准方案不支持，引导走 `@UseSignature` 自定义方案 |
| JSON content-type 且实际带体但 rawBody 缺失 | **401 拒绝**——必为 rawBody 装配缺失或异常链路，fail-closed |

> 为什么「绑原始字节」而不是「参数排序规范化拼接」（部分开放平台的做法）？因为 JSON 嵌套结构的规范化序列化规则（键序、数组、类型差异、null、编码……）极难跨端一致，是历史上验签 bug 的最高发来源；「签的 = 发的」在密码学上最完备且对 body 格式零假设，与主流支付/Webhook 验签（绑原始请求体）同路线。特殊参数格式的对外接口经自定义方案接管（见 2.3）。

**完整算例**（可手工复现，密钥 `demo-secret`）：

```text
请求：POST /api/orders  Content-Type: application/json
请求体：{"name":"CNY"}
请求头：sign: <下方计算值>  timestamp: 1760000000000  noncestr: demo-nonce-001

signString（5 段以 \n 连接）:
POST\n/api/orders\n{"name":"CNY"}\n1760000000000\ndemo-nonce-001

sign = HMAC-SHA256(上串, "demo-secret")
     = 999bc28b9eca5cfa2cba144331ed1369ec4cb1a106b33ddc722e0cb885d604bb
```

### 2.3 签名方案模型（豁免与自定义格式的统一扩展点）

签名验证抽象为**可插拔的签名方案（SignatureScheme）**，豁免与自定义格式是同一模型的两种表达：

```typescript
// server/src/common/signature/interfaces/signature-scheme.interface.ts
export interface SignatureScheme {
  /** 方案唯一名，@UseSignature('名称') 引用 */
  readonly name: string
  /** 执行验签：通过时正常返回；失败时 throw（Guard 统一转 401，不透出原因） */
  verify(context: SignatureContext): void | Promise<void>
}

export interface SignatureContext {
  /** 原始 HTTP 请求：方案可自行取 headers / query / body（自定义方案的签名材料可不在标准位置） */
  request: Request
  /** 原始请求体字节（仅 JSON / urlencoded 且应用以 rawBody: true 装配时有值） */
  rawBody?: Buffer
  /** 签名密钥（signature.secret 配置） */
  secret: string
  /** 签名有效时间窗（毫秒，signature.expireMs 配置），自定义方案可自行决定是否使用 */
  expireMs: number
}
```

| 扩展方式 | 用法 | 场景 |
| --- | --- | --- |
| 默认方案 `standard` | 无需任何标记，写方法自动套用 | 标准 JSON API（本框架绝大多数接口） |
| `@SkipSignature()` | 装饰控制器或方法 | 对外接口不需要签名（如第三方主动推送、已由网关验签的回调） |
| `@UseSignature('方案名')` | 装饰控制器或方法（方法级优先） | 对外接口有独特参数格式（签名参数在 query、body 是 form/XML、自有验签规则） |

两个装饰器均支持控制器级（整个控制器生效）与方法级（单个接口生效），方法级优先于控制器级。

**注册自定义方案**（业务模块 `onModuleInit` 中向注册表注册）：

```typescript
// 例：某对外 XML 报文接口的模块内
@Injectable()
export class OpenApiXmlSignatureScheme implements SignatureScheme {
  readonly name = 'openapi-xml'

  verify(ctx: SignatureContext): void {
    // 从 ctx.request.query 取对方约定的签名参数，按对方规则验签；
    // ctx.rawBody / ctx.secret / ctx.expireMs 按需使用
    // 失败直接 throw，Guard 统一转 401「签名校验失败」
  }
}

@Module({ providers: [OpenApiXmlSignatureScheme] })
export class OpenApiModule implements OnModuleInit {
  constructor(
    private readonly registry: SignatureSchemeRegistry,
    private readonly scheme: OpenApiXmlSignatureScheme,
  ) {}

  onModuleInit() {
    this.registry.register(this.scheme)   // 重名注册直接抛错（启动期暴露冲突）
  }
}

// 控制器上：@UseSignature('openapi-xml')
```

> 注意：urlencoded / multipart / text 请求**不会**产生 rawBody（Nest 仅对 JSON 与 urlencoded 两种 content-type 缓冲原始体，且 urlencoded 在本框架中不使用）。自定义方案需要 XML/form 原文体时，需自行从流读取或注册自己的原始体缓存中间件——这正是把这类接口交给自定义方案而非硬塞进标准方案的原因。

### 2.4 防重放设计

标准方案两层防线：

1. **双向时间窗**：`|Date.now() - timestamp| > expireMs` 即拒绝——过去方向拦截过期请求，**未来方向同样拦截**（防攻击者把时间戳设到远未来绕过「只查过去」的校验漏洞）
2. **nonce 一次性消费**：`nonceStore.tryConsume(nonce, 2 × expireMs)`——nonce 首次出现即记录并在窗口内拒绝重复；窗口取 2 倍时间窗保证「时间戳还有效的请求，其 nonce 必然仍被记录」

`InMemoryNonceStore`（`server/src/common/signature/nonce-store/in-memory-nonce-store.ts`）实现要点：

- `Map<nonce, 过期时刻>`；消费时惰性清理过期项；容量超上限（10000）触发强制清理，防恶意 nonce 填充内存
- 以 `NonceStore` 接口抽象注入（`NONCE_STORE` token），未来多实例部署可替换为 Redis 实现（`SETNX + TTL`），业务代码零改动

### 2.5 配置项与 fail-fast

配置链路遵循全仓约定：**环境变量 → configuration.ts → ConfigService**。

| 配置项 | 环境变量 | 默认 | 说明 |
| --- | --- | --- | --- |
| `signature.enabled` | `SIGNATURE_ENABLED` | `false` | 总开关；关闭时 Guard 直接放行。`.env.example` 模板值为 `true`（新项目按模板初始化即启用） |
| `signature.secret` | `SIGNATURE_SECRET` | `''` | HMAC 密钥，与前端 `VITE_SIGN_SECRET` 保持一致 |
| `signature.expireMs` | `SIGNATURE_EXPIRE_MS` | `300000` | 签名有效时间窗（毫秒），默认 5 分钟 |

**fail-fast**：`SignatureModule` 启动时校验——`enabled` 且 `secret` 为空直接抛错阻止启动。安全机制不得静默失效：与其「配错了但服务照常跑、签名全部 401」或更糟的「静默放行」，不如启动期就把配置错误暴露出来。

### 2.6 前端接入

**自动签名**（`web/src/api/http.ts` 请求拦截器）：写方法请求自动完成——

1. `bodyText = config.data === undefined ? '' : JSON.stringify(config.data)`
2. 以 `resolveSignPath(baseURL, url)` 计算 pathname，调 `signRequest` 生成三件套头
3. **同一 `bodyText` 字符串本体作为请求体发送**并显式声明 `Content-Type: application/json`——保证「签的内容 = 发的内容」，不依赖 axios 内部序列化行为（axios 对 string body 不会自动加 json 头，缺失会绕过服务端 JSON 解析导致验签必败，必须显式设置）
4. 无 body 的动作型请求（`data` 为 undefined）：空串参与签名，不发送 body、不设 Content-Type

GET/HEAD/OPTIONS 不进签名分支，零开销。

**手动签名**（`web/src/api/signature.ts` 导出 `signRequest(url, body?)`）：非 axios 发出的请求（如 Element Plus 上传控件、第三方 SDK 直连）在自定义请求逻辑中调用，返回值直接并入请求头。

密钥经 `VITE_SIGN_SECRET` 环境变量注入（`.env.development` / `.env.production`），不硬编码在源码中。

## 3. 接口约定

### 3.1 请求头三件套

| 头 | 必填（写方法） | 取值 |
| --- | --- | --- |
| `sign` | 是 | 签名串的 HMAC-SHA256 小写 hex |
| `timestamp` | 是 | 毫秒 Unix 时间戳字符串 |
| `noncestr` | 是 | 一次性随机串（前端用 `crypto.getRandomValues` 生成 32 位 hex） |

### 3.2 服务端响应

校验通过：请求正常进入后续处理链。校验失败（任何原因）：

```json
HTTP 401
{ "code": 401, "message": "签名校验失败" }
```

**所有失败原因共用同一响应**（缺头 / 时间戳过期或超前 / nonce 重放 / body 判定拒绝 / 签名不匹配）——不给探测者反馈「差哪一步」，具体原因仅写入服务端日志（Nest `Logger`）。

### 3.3 服务端扩展 API 速查

| 能力 | 入口 | 说明 |
| --- | --- | --- |
| 豁免签名 | `@SkipSignature()`（`server/src/common/signature/decorators/`） | 控制器级/方法级 |
| 自定义方案 | `@UseSignature('name')` + `SignatureSchemeRegistry.register()` | 见 2.3 完整示例 |
| 方案接口 | `SignatureScheme` / `SignatureContext` / `NonceStore` | `server/src/common/signature/interfaces/` |
| nonce 存储替换 | `NONCE_STORE` token 提供 `useClass`/`useValue` 覆盖 | 现默认内存实现 |

## 4. 边界与异常

1. **统一 401 的取舍**：失败原因不透出给客户端（防探测），代价是调用方排障只能对照本文档自查；服务端日志保留完整原因（注意：恶意流量会刷日志量，生产可按需对签名失败日志限流/采样）
2. **多实例部署局限**：`InMemoryNonceStore` 是单进程内存存储，横向扩容后各实例 nonce 不互通（防重放窗口内可在另一实例重放成功）。单实例部署无此问题；多实例需以 Redis 实现替换 `NONCE_STORE`
3. **query 参数不参与签名**：标准方案只签 path 不签 query——写方法的业务参数应放 body（RESTful 约定 query 仅承载过滤/分页等读语义）。确需签名覆盖 query 的接口走自定义方案
4. **标准方案限定 JSON**：非 JSON content-type 带体的写请求直接 401（见 2.2 判定表）。文件上传（multipart）等内容不参与标准签名——上传接口可 `@SkipSignature()` 后由业务自验，或自定义方案接管
5. **Swagger try-it-out 写接口会被拦**：Swagger UI 发起的写请求不带签名头，将收到 401。这是已知取舍：签名头由前端拦截器注入，Swagger 不承载该能力；只读调试请用 GET 接口，写接口调试用带签名的脚本（见验收标准 5.3）
6. **URL 编码与代理改写**：path 以 URL 编码后的形式参与签名（两端一致即可）；若未来给 Vite 代理或网关加 path rewrite，需同步两端签名 path 约定；反向代理改写**请求体**（如注入字段）会使签名失效——链路上不得有改写 body 的组件
7. **时钟偏移**：双向时间窗隐含「两端时钟偏移必须小于 expireMs」的假设；跨机房/容器环境请确保 NTP 正常，或按需调大 `SIGNATURE_EXPIRE_MS`

## 5. 验收标准

### 5.1 测试覆盖

- `server/src/common/signature/` 横切设施全分支单测：标准方案全部失败分支与 body 判定四分支、Guard 开关/豁免/方法/方案分发、nonce 存储首见/重放/过期/容量、注册表重名拒绝
- `server/test/signature.e2e-spec.ts` 真链路正反例（正确签名 200、无头/篡改/错密钥/过期/重放 401、豁免与自定义方案）
- 前后端 `buildSignString` 对等守护：两端单测断言**同一组固定向量**的 HMAC hex 输出，任何一端构造漂移立即测试失败

### 5.2 `pnpm check` 全绿

含 lint、类型检查、前后端单测、后端 e2e。

### 5.3 手动验证（正反例）

`server/.env` 设置 `SIGNATURE_ENABLED=true` 与密钥后启动，可验证：

```bash
# 反例：无签名头 → 401 {"code":401,"message":"签名校验失败"}
curl -i -X POST http://localhost:3000/api/<写接口> -H 'Content-Type: application/json' -d '{"name":"CNY"}'

# 正例 + 反例（篡改 body / 重放）：按 2.2 算例规则生成签名发送
# 篡改 body（签名按 A 生成、实际发 B）→ 401；同一三件套原样重发 → 第二次 401
```
