# 权限设计

> 本文档以 n-2 同名设计文档为底稿改写（B 档翻译），剔除菜单表、角色-菜单分配、菜单 id 段位等章节（[ADR-001](../决策/ADR-001-菜单与路由的权限承载方式.md)：菜单不落库）。
> 实施细节（批次拆分、迁移时序、e2e 组织）见《[批次四-认证授权RBAC设计](../规划/批次四-认证授权RBAC设计.md)》；认证与会话决策见 [ADR-003](../决策/ADR-003-认证与会话方案.md)。

## 1. 背景与设计原则

企业级底座必须回答「谁能用哪个页面、谁能调哪个接口、谁能看到哪个按钮」。本设计的核心哲学：

> **开发阶段能确定的内容严格在代码层面落实，不下放到配置。**

| 内容 | 承载 |
| --- | --- |
| 权限点是什么（串 / 中文名 / 归属） | **代码**（权限点注册表，编译期常量唯一出处） |
| 谁拥有什么（用户-角色、角色-权限分配） | **数据库**（运行期数据） |
| 页面与菜单结构 | **代码**（前端静态路由树，ADR-001；菜单 = 按权限过滤后的路由投影） |

这是反 ruoyi 模式的刻意选择：不把按钮权限点塞进菜单表，杜绝「种子 SQL 插按钮行 + 后端注解串 + 前端 `v-hasPermi` 串」三处手抄同一权限串的漂移面。**权限串的字面量唯一出处是注册表常量**，注解、指令、分配校验一律引常量——与错误码常量同一哲学。

两类受控资源彻底分离：

- **页面可见性**：前端静态路由 `meta.permission` + 守卫与菜单过滤承担（ADR-001）
- **操作权限**：权限串 + 后端 Guard 逐接口校验 + 前端 `v-hasPermi` 按钮渲染

## 2. 权限模型

标准 RBAC：用户 —（多对多）— 角色 —（多对多）— 权限点。相比 n-2 **少菜单表与角色-菜单表两张**（页面可见性不落库）。

### 2.1 表结构

四张表全在 system 模块（`server/src/modules/system/entities/`），继承规则：

- `UserEntity` / `RoleEntity`：继承 `BaseEntity`（uuid 主键 + 审计列 + TypeORM 原生软删）
- `UserRoleEntity` / `RolePermissionEntity`：**纯关联值对象，不继承 BaseEntity，物理删除**——差集增量分配逐行 delete；若走软删，唯一索引会被历史行占位打穿（同一对关联删除后无法重新分配）

| 表 | 列 | 唯一索引 |
| --- | --- | --- |
| `system_users` | id / username / password（BCrypt）/ nickname / status / 审计列 / deleted_at | `(username)` |
| `system_roles` | id / name / code / sort / status / remark / 审计列 / deleted_at | `(code)` |
| `system_user_role` | id / user_id / role_id / created_at | `(user_id, role_id)` |
| `system_role_permission` | id / role_id / permission / created_at | `(role_id, permission)` |

列形态遵循批次二建表类型规约：uuid 主键、`boolean` 状态、`timestamptz` 时间、蛇形小写、逻辑外键无物理约束。`status` 语义：`1` 启用 / `0` 停用。

### 2.2 种子数据

手写迁移承载（不引入 seed 框架）：

- `admin` 用户（BCrypt 散列静态写入，初始口令 `admin123`）
- `super_admin` 角色（内置，remark 注明不可删除）
- `admin ↔ super_admin` 绑定行（**无权限关联行**——super_admin 全集在读取侧收敛）

内置保护（代码层常量约定）：

- 内置用户：更新 / 删除 / 重置密码抛 `USER_ADMIN_OPERATION_FORBIDDEN`
- 内置角色：改名 / 停用 / 删除抛 `ROLE_BUILTIN_FORBIDDEN`；`super_admin` 为保留字，创建角色拒绝

## 3. 权限点代码注册表

### 3.1 形态

n-2 因「Java 注解只接受编译期常量」拆 interface + enum 双层；TS 装饰器收普通表达式，**单层数组即唯一出处**（`server/src/modules/system/permissions.ts`）：

```ts
export interface PermissionPoint {
  readonly code: string    // 三段冒号小写：'system:user:query'
  readonly label: string   // 中文名（角色分配界面展示）
}

export const SYSTEM_PERMISSIONS: readonly PermissionPoint[] = [
  { code: 'system:user:query', label: '用户查询' },
  // …
]
```

配套 `PermissionRegistry`（`@Global`）：启动期校验 **code 全局唯一**、**首段 === 提供模块**、**模块名不重复**；提供 `allCodes()` / `contains()`。违反契约启动期失败（fail-fast，与签名密钥同款纪律）。

**多模块聚合（批次六落地）**：Registry 暴露 `registerModule({ module, points })` 实例方法，各业务模块在自己的 `onModuleInit` 钩子中注入 Registry 并登记自有清单（依赖方向业务 → system，`@Global` 导出直接注入）；注册即校验，任何违规在监听端口前抛错。system 自有清单走同一注册入口（语义对称）。接入步骤见[新模块接入指南](新模块接入指南.md)。

### 3.2 命名规范

权限串三段冒号小写 `模块:域:操作`（与错误码分段同构）：`system:user:create`。首段必须等于提供模块的注册名（注册表启动校验）。

## 4. 权限校验链路

### 4.1 加载链（每个受保护请求）

```
请求 → SignatureGuard（写方法验签，外层防线）
     → JwtAuthGuard：@Public() 豁免 → 解析 Bearer JWT → 查库校验用户存在且启用
       → requestContext.setUserId()（激活审计填充）
     → PermissionsGuard：无 @RequirePermissions 仅需登录
       → 查权限集合 → 任一命中放行，否则 403
```

- 401（未登录 / token 无效或过期 / 用户不存在或停用）与 403（已登录但无权限）均为**真实 HTTP 状态码**，业务码落通用段 401 / 403
- **权限不塞 JWT payload**：角色与权限逐请求现查——角色变更、权限回收、用户禁用全部即时生效（ADR-003 存在性校验语义的延伸）

### 4.2 super_admin 全集语义

- 判定：用户持有的**启用**角色中存在 `code === 'super_admin'`（精确值比对；code 有唯一约束，创建同名角色不可能）
- 全集 = 注册表 `allCodes()`：注册表新增权限点，超管自动拥有，无需维护关联（分配界面该角色勾选集为空属预期）
- 前端**无超管特判**：全集已在后端 `get-permission-info` 的 `permissions` 数组里收敛

### 4.3 读写不对称策略

| 侧 | 行为 | 理由 |
| --- | --- | --- |
| 读取（回显 / 下发） | 返回库内权限串全集，**不过滤**注册表 | 历史未注册串命中不了任何注解常量（注解只能引已登记常量），无提权面；免掉每次鉴权 join 枚举的成本 |
| 写入（分配） | 逐串 `registry.contains()` 校验，未登记抛 `ROLE_PERMISSION_UNKNOWN` | 拒绝脏数据入库，权限串自始有唯一出处 |

### 4.4 停用语义

- 停用**角色**：其权限即时从用户权限集合中消失（查询仅计入 `status = 启用` 的角色）
- 停用**用户**：登录被拒（`AUTH_LOGIN_DISABLED`）；已发 token 在 Guard 存在性校验处即时失效

## 5. 前端集成

### 5.1 数据源与登录链路

- 登录 `POST /api/system/auth/login` 只返回 `{token}`；守卫首次放行前调 `GET /api/system/auth/get-permission-info` 拉齐 `{user, roles, permissions}` 存入 auth store（**无 menus**——菜单由静态路由过滤而来）
- token 存 `localStorage`（key `N1_TOKEN`，纯字符串），请求经 http 拦截器注入 `Authorization: Bearer <token>`；401 清令牌带 redirect 整页跳登录

### 5.2 三层控制

| 层 | 机制 | 失败表现 |
| --- | --- | --- |
| 菜单（显示层） | `buildMenuTree` 按 `meta.permission` 过滤，布局组件零改动 | 菜单项不出现 |
| 路由（页面级） | 守卫 beforeEach 校验 `to.meta.permission` | 跳 404（不泄露页面存在性，与菜单不可见语义一致） |
| 按钮 / 接口 | 前端 `v-hasPermi`（无权移除节点）；后端 `@RequirePermissions`（无权 403） | 按钮不渲染；接口 403 |

**前端只是显示层，后端 Guard 是唯一安全边界**——绕过前端直调接口由后端兜底。

### 5.3 新增受控页面接入指引

1. 注册表登记权限点（`SYSTEM_PERMISSIONS` 加一行）
2. 路由模块文件加路由，`meta` 挂 `title / icon / permission`
3. 每个受控接口挂 `@RequirePermissions(常量)`
4. 每个受控按钮挂 `v-hasPermi="常量"`
5. 角色分配界面勾选权限（或 SQL 种子）——**无需同步任何菜单表**（ADR-001 红利）

## 6. 安全分析

| 风险 | 对策 |
| --- | --- |
| 账号枚举 | 登录时用户不存在与密码错误同码同文案（`AUTH_LOGIN_FAILED`） |
| 密码泄露 | BCrypt 散列存储（cost 10），日志与响应永不回传散列；DTO whitelist 拒绝多余字段 |
| token 伪造 | JWT HMAC 签名 + 密钥经 `.env` 注入，空密钥启动 fail-fast |
| 禁用用户残留会话 | Guard 逐请求查库存在性校验（ADR-003，即时失效） |
| CSRF | 仅认请求头 Bearer token，不读 cookie |
| 越权直调接口 | 后端 Guard 逐接口校验（唯一安全边界），前端过滤仅为体验层 |
| 权限串漂移 | 注册表唯一出处 + 启动期唯一性校验 + 写入侧登记校验 |

## 7. 测试策略

按 [rules/testing.md](../../rules/testing.md) 风险分级：

- **契约守护类（必测）**：注册表串唯一 / 首段校验；`@Public` 豁免优先级；401 / 403 语义与通用段码映射；读写不对称两侧
- **重点分支覆盖**：登录三态（成功 / 同码失败 / 停用）、super_admin 全集、停用角色剔除、守卫五分支（登出清理 / public / 未登录 / 加载权限 / 无权 404）
- **e2e**：server 认证 e2e（Repository 内存桩）；浏览器登录链路四用例（成功 / 失败 / 未登录重定向 / 退出）
- 纯赋值（实体 / DTO / 常量表）不写单测，类型系统守护
