## 1. 需求背景

批次一至五交付了完整底座：工程化门禁、数据层基建、前端门面、RBAC 认证授权、系统管理六域。但「为 AI 编码服务的工程基座」（vibe coding first）的核心承诺尚未兑现——**AI 照什么样板从 0 到 1 生成一个新业务模块？** 可模仿的样板比文档描述更有效（规划 C3）。

本批次以**示例商品管理**（虚构业务，最小但完整的单表 CRUD）为载体，演示新业务模块的标准路径：段位登记 → 实体与迁移 → 后端域四件 → 前端页面 → 测试与验收，并沉淀《[新模块接入指南](../指南/新模块接入指南.md)》。

1. **权限注册表多模块聚合**：当前 `PermissionRegistry` 硬编码只聚合 system 一份清单（`permissions.ts` 注释已预告本批次扩展）——这是 demo 作为第二个业务模块触发的框架改造，对应 n-2 的 `PermissionProvider` 落地；

## 3. 方案设计

### 3.1 权限注册表多模块聚合（n-2 PermissionProvider 的 NestJS 翻译）

**n-2 形态**：Spring 容器注入 `List<PermissionProvider>`（system api 包定义契约，业务模块 `@Component` 实现即被聚合），跨 jar 天然聚合。

**n-1 翻译背景**：NestJS 的 DI 跨模块注入有方向限制——demo 模块的 provider 无法被 SystemModule 上下文看到（除非 system 反向 import demo，依赖方向错误）。故不照搬 DI 注入形态，改为**注册表实例方法 + 模块生命周期钩子**：

```ts
// system/permissions.ts 扩展（Registry 数据源从构造期定死改为可聚合 Map）
export interface PermissionModuleDefinition {
  /** 模块注册名，须与权限串首段一致（如 'demo'） */
  module: string
  points: readonly PermissionPoint[]
}

@Injectable()
export class PermissionRegistry {
  private readonly modules = new Set<string>()
  private points = new Map<string, PermissionPoint>()

  constructor() {
    // system 自有清单走同一注册入口（保底非空，语义与聚合对称）
    this.registerModule({ module: SYSTEM_MODULE_NAME, points: SYSTEM_PERMISSIONS })
  }

  /** 业务模块接入入口：即时校验（模块名重复 / 首段不符 / 权限串全局冲突均启动期抛错） */
  registerModule(def: PermissionModuleDefinition): void {
    if (this.modules.has(def.module))
      throw new Error(`权限模块「${def.module}」重复注册`)
    this.modules.add(def.module)
    this.points = validatePermissionPoints(def.module, def.points, this.points)
  }

  // allCodes() / allPoints() / contains() 对外签名不变，数据源改为聚合 Map
}
```

业务模块接入（demo 全套动作，写进接入指南）：

```ts
// modules/demo/demo.module.ts
export class DemoModule implements OnModuleInit {
  constructor(private readonly permissionRegistry: PermissionRegistry) {} // @Global SystemModule 导出，业务 → 系统方向正确
  onModuleInit(): void {
    this.permissionRegistry.registerModule({ module: DEMO_MODULE_NAME, points: DEMO_PERMISSIONS })
  }
}
```

| 关注点 | 结论 |
| --- | --- |
| fail-fast 时机 | `registerModule` 内即时校验（复用既有纯函数 `validatePermissionPoints` 的首段 + 全局唯一校验，`existing` 传聚合 Map 实现跨模块查重），任何违规在 `onModuleInit` 阶段抛错阻止启动——不晚于监听端口 |
| 请求期一致性 | `PermissionsGuard` / `PermissionService` 均在请求期读取，此时全部模块已注册完毕（Nest 先跑完所有 `onModuleInit` 再 `listen`） |
| 消费方零改动 | super_admin 全集（`allCodes`）、权限点清单接口（`allPoints`）、分配写入校验（`contains`）数据源自动扩至 34 项 |
| 依赖方向 | demo → system（`@Global` 导出直接注入），与 n-2「业务模块依赖 n-module-system」同向 |

### 3.3 数据模型与迁移

**实体 `DemoProductEntity`**（继承 `BaseEntity`：uuid 主键 + 审计列 + 软删；蛇形命名）：

| 列 | 类型 | 说明 |
| --- | --- | --- |
| name | varchar(100)，`uk_demo_product_name` 部分唯一索引（`WHERE deleted_at IS NULL`） | 商品名称 |
| category | varchar(100) | 分类，存字典 `demo_product_category` 的 dictValue（英文语义串） |
| price | numeric(12,2) | 金额；PG 驱动读出为 string，`toVo` 统一 `Number()` 转数值出口（样板层面够用；真实大金额业务建议 string 全链——留痕在接入指南） |
| status | boolean，默认 true | 状态；前端复用 `common_status` 字典（boolean 直传命中），示范跨模块复用字典 |
| description | varchar(500)，null | 描述 |

**迁移两段**（时间戳接续现有 5 个迁移之后）：

1. `CreateDemoTables`（`migration:generate` 从实体派生）：建 `demo_product` 表 + 部分唯一索引；
2. `DemoSeed`（手写，id 常量入 `modules/demo/demo.constants.ts` 与代码同源）：
   - 字典类型 `demo_product_category`（示例商品分类）+ 4 条数据：`digital` 数码（primary）/ `clothing` 服饰（success）/ `food` 食品（warning）/ `book` 图书（info）——**系统管理之外的业务模块消费字典的首个示范**；
   - 3 条示例商品（状态混合，示范数据形态）。

**与 n-2 的翻译差异**：BIGINT 雪花 → uuid；SMALLINT 0/1 → PG boolean；TIMESTAMP → timestamptz（批次二建表规约）；**菜单种子不做**（ADR-001，前端静态路由承担）。

### 3.4 接口清单与后端域四件

**接口六件**（最终路径 `/api/demo/product/**`，照 n-2 同构）：

| 接口 | 动词 | 权限点 | 说明 |
| --- | --- | --- | --- |
| `/demo/product/page` | GET | `demo:product:query` | 分页：name 模糊 / category 等值 / status 等值 |
| `/demo/product/get?id=` | GET | `demo:product:query` | 单查 |
| `/demo/product/list` | GET | `demo:product:query` | 启用商品全量（**下拉数据源示范**，n-2 同款语义） |
| `/demo/product/create` | POST | `demo:product:create` | `@OperateLog('商品管理', '新增商品')` |
| `/demo/product/update` | PUT | `demo:product:update` | `@OperateLog('商品管理', '修改商品')` |
| `/demo/product/delete/:id` | DELETE | `demo:product:delete` | `@OperateLog('商品管理', '删除商品')`（软删，无关联表不连带） |

**域四件**（照 post 域 1:1 平移，`modules/demo/product/` + `modules/demo/entities/`）：

| 层 | 要点 |
| --- | --- |
| controller | `DemoProductController`；DTO 值导入纪律（import type 擦除元数据会被 whitelist 拒绝）；返回裸业务数据由 TransformInterceptor 包裹 |
| dto | `ProductPageDto`（name / category / status 可选过滤 + PageParamDto）；`ProductCreateDto` / `ProductUpdateDto`（UpdateDto 首字段 `@IsUUID() id`）；price 用 `@IsNumber({ maxDecimalPlaces: 2 })` + `@Min(0)`；中文 message |
| service | `DemoProductService`：`validateNameAvailable`（查重排除自身，`Not(excludeId)`）、`getExistsProduct`（不存在抛 `PRODUCT_NOT_EXISTS`）、`toVo` 白名单映射（price `Number()` 转换）；`listEnabled` 按 status true + id 倒序 |
| 实体 | 见 §3.3 |

**demo 不需要 @Public / @SkipSignature**（业务 CRUD 接口默认走完整 Guard 链：签名 → JWT → 权限）。

## 5. 边界与不做清单

1. **不做主子表 / 树表 / Excel 导入导出 / 前后端代码生成器**（样板保持单表最小形态；生成器在规划「不吸收清单」已定）
2. **不做工作流接入样板**（n-2 §10 demo 请假，n-1 无 BPM，不吸收清单已定；接入指南不含该步）
3. **不做菜单种子与菜单管理**（ADR-001）
4. **不引入任何新依赖**
5. **不做商品图片上传 / 富文本**（描述为纯文本 textarea）
6. **金额精度从简**：全链 number（numeric 列 toVo 转 number），大金额场景的 string 全链建议留在接入指南说明，不在样板实现
7. **不改 system 域任何业务逻辑**（Registry 改造仅动注册表聚合机制，消费方零改动）

## 6. 验收标准

1. 根目录 `pnpm check` 全绿（lint + 类型检查 + 前后端单测 + 后端 e2e），存量契约零破坏
