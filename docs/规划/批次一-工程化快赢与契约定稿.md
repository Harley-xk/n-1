# 批次一：工程化快赢与契约定稿设计

> 本文是 [n-2 消化吸收规划](n-2消化吸收规划.md) 批次一的实施设计文档。批次一的特征是**零业务耦合**：全部改动落在工程化设施与前后端公共契约上，不引入任何业务模块，为后续批次（数据层、前端门面、认证授权）铺定地基。

## 1. 需求背景

n-1 当前只有「骨架 + 两个横切设施」（签名验证、统一响应/异常处理），错误码仍是单符号形态（`-1`），多模块并行后不可检索、不可按模块治理；浏览器 e2e 不拉起后端，测不到全链路；web 单测为 node 环境，测不了组件；CLAUDE.md 缺少「当前状态」进度日志，新会话恢复上下文慢。六项改造均属规划 C1 / C4 / B6 / B7 / A9 / C6 条目，决策点 1 / 7 / 9 已定稿（见规划 §7）。

## 3. 方案设计

### 3.1 分段错误码体系（B7，ADR-002 实施）

#### 3.1.1 码结构与位数定稿

九位整数 = **模块段 3 位 + 子域段 3 位 + 序号段 3 位**（与 n-2 一致，降低翻译成本）：

```text
1 001 002 003
│ │   │   └── 序号段：模块内错误序号，001 起
│ │   └────── 子域段：模块内子域（如 system 的 用户/角色），000 为整模块共用
│ └────────── 模块段：001 起，业务模块接入时登记
└──────────── 数值含义：整体是一个 number（1001002003），成功码 0 不变
```

- **通用段**：模块 `000`、子域 `000`，序号段**借用 HTTP 语义码**（400 / 401 / 403 / 404 / 405 / 500 …）与一个业务兜底码 999。因模块段子域段均为 0，通用段码在数值上恰等于序号段本身（如 `000-000-404` 就是 `404`）——**框架级错误的 code 数值与现行实现完全一致，存量契约零破坏**。
- **默认业务码 `000-000-999`（= 999）**：`BusinessError` 未指定错误码时的默认值，替代原 `-1`。含义是「未分类业务错误」；业务模块接入后应引用自己模块的常量，逐步消除 999。
- 模块段位表：批次一仅建立规则与通用段；首个业务段位（system = `001`）随批次四登记，后续按批次六「新模块接入清单」领取。

#### 3.1.2 新增 `ErrorCode` 值对象与通用段常量

`server/src/common/errors/error-code.ts`：

```ts
export class ErrorCode {
  constructor(readonly code: number, readonly message: string) {}
}

export const GlobalErrorCode = {
  INVALID_REQUEST_PARAM: new ErrorCode(400, '请求参数不合法'),
  UNAUTHORIZED: new ErrorCode(401, '账号未登录'),
  FORBIDDEN: new ErrorCode(403, '没有该操作权限'),
  NOT_FOUND: new ErrorCode(404, '请求不存在'),
  METHOD_NOT_ALLOWED: new ErrorCode(405, '请求方法不支持'),
  INTERNAL_SERVER_ERROR: new ErrorCode(500, '服务器内部错误'),
  BUSINESS_ERROR: new ErrorCode(999, '业务处理失败'),
} as const
```

错误码常量是唯一出处：业务抛错引用常量，不写裸数字（与 ADR-001 权限点同一哲学）。业务模块的常量表落各自模块目录（如 `modules/system/error-codes.ts`），通用段不扩张。

#### 3.1.3 `BusinessError` 改造

- `options.code` 类型从 `number` 收紧为 **`ErrorCode`**（编译期常量引用，杜绝裸数字）；缺省取 `GlobalErrorCode.BUSINESS_ERROR`（999）。
- `message` 保持必填字符串：错误场景通常需要上下文消息，`ErrorCode.message` 是兜底文案，供过滤器映射场景使用。

#### 3.1.4 异常过滤器与拦截器改造

| 分支 | HTTP status | code（改前 → 改后） | message |
| --- | --- | --- | --- |
| `HttpException`（Nest 内置） | `getStatus()` | `status` → `status`（不变，数值即通用段码） | 不变（DTO 校验数组拼接等） |
| `BusinessError` | `exception.status` | `-1` → `exception.code`（默认 999） | 不变 |
| 未知 `Error` 兜底 | 500 | `-1` → `500`（`GlobalErrorCode.INTERNAL_SERVER_ERROR`） | 不变（「服务器内部错误」） |
| 拦截器防御分支（非 2xx 仍有返回值） | 保持 | `-1` → `500` | — |

`ApiResponse` 接口注释同步：`0` 成功；非 `0` 为九位分段错误码。

#### 3.1.5 前端判定与文档

- `web/src/api/http.ts`：成功判定由符号比较 `code < 0` 改为 **`code !== 0`**（分段码全为正整数，符号语义失效；成功码 0 不变）。
- 《统一响应与异常处理设计》§2.2 / §2.3 / §2.5 / §3 / §2.8 / §5 与变更记录同步改写；ADR-002 补实施定稿记录。

#### 3.1.6 存量测试影响面

| 测试 | 影响 |
| --- | --- |
| `http-exception.filter.spec.ts` | BusinessError 默认码断言 `-1` → `999`；未知异常 `-1` → `500`；补「传入自定义 ErrorCode 透传」用例 |
| `transform.interceptor.spec.ts` | 防御分支 `-1` → `500` |
| `exception-filter.e2e-spec.ts` | `code < 0` 断言 → `code` 为 `999` |
| `app.e2e-spec.ts` / `signature.e2e-spec.ts` | **零改动**（code 0 / 404 / 401 数值不变，验证了通用段数值兼容性） |
| web `http.spec.ts` | 零改动（只走成功路径） |

### 3.2 访问日志与安全响应头中间件（B6）

n-2 的 servlet Filter 翻译为 **Nest middleware**（经 `AppModule implements NestModule` 注册，而非 `main.ts` 的 `app.use()`）——与全局过滤器/拦截器同一注册哲学：e2e 测试 `imports: [AppModule]` 自动继承，无需手动复制装配。

注册顺序（`configure` 中先 apply 者先执行）：**安全响应头 → 访问日志**，均 `forRoutes('{*splat}')` 全路由（Nest 11 / Express 5 的通配符语法）；路径过滤不依赖路由表，由中间件内部判断，保证 404 等未知路径同样被覆盖。

#### 3.2.1 安全响应头中间件

`server/src/common/middleware/security-headers.middleware.ts`，对**所有响应**（含 Swagger 文档页）注入：

| 头 | 值 | 防御目标 |
| --- | --- | --- |
| `X-Content-Type-Options` | `nosniff` | 禁止浏览器 MIME 嗅探 |
| `X-Frame-Options` | `DENY` | 禁止被嵌入 iframe（防点击劫持） |
| `Cache-Control` | `no-cache, no-store, max-age=0, must-revalidate` | 响应内容不落缓存（防敏感信息残留） |
| `Pragma` | `no-cache` | 同上（HTTP/1.0 兼容） |
| `Expires` | `0` | 同上 |
| `Referrer-Policy` | `no-referrer` | 不泄漏来源地址 |

刻意不加：`X-XSS-Protection`（浏览器已废弃该机制）、CSP 与 HSTS（HSTS 仅 HTTPS 有意义，与 CSP 同属部署层策略，由 nginx / 前端服务按环境注入）——沿用 n-2 已论证的取舍。

#### 3.2.2 访问日志中间件

`server/src/common/middleware/access-log.middleware.ts`：

- 仅记录 `/api/` 前缀的请求（`/api-docs` 文档与静态资源不记；用 `/api/` 前缀而非 `/api`，恰好排除 `/api-docs`）
- 监听 `response` 的 `finish` 事件输出一行：`[方法] 路径 -> 状态码(code=业务码), 耗时 Nms`
- 日志走 Nest `Logger`（上下文 `ApiAccessLog`）
- **业务 code 回填机制**（n-2 request attribute 的翻译）：`server/src/common/utils/response-code.ts` 提供 `setResponseCode(request, code)`；响应包装拦截器（成功路径）与异常过滤器（失败路径）在产出 code 时回填到 request 对象，访问日志在 `finish` 时读取——HTTP 已流式写出后无法再取响应体，回填是唯一通路

### 3.3 web vitest 切 jsdom（A9）

- `web/vite.config.ts` 的 `test.environment`：`node` → **`jsdom`**；`web/package.json` devDependencies 增加 `jsdom`、`@vue/test-utils`（版本对齐 n-2：`jsdom ^30`、`@vue/test-utils ^2.5`）
- 存量 3 个 spec（http / signature / counter）在 jsdom 下回归：`crypto.subtle`（Node 全局 webcrypto）、`FormData`（jsdom 原生）均可用，预期零改动
- 补一个**组件测试样例**（`NotFoundView` 挂载渲染断言）：证明组件测试链路可用，为批次三布局组件测试铺路。按 rules/testing.md 风险分级，仅落一个能力验证样例，不逐组件配 spec

### 3.4 prettier + lint-staged（C6，决策 7）

- **工具分工（实施期实验定稿）**：n-1 的 ESLint 使用 `@stylistic` `customize()` 完整规则集（`max-statements-per-line`、`vue/max-attributes-per-line`、`vue/script-indent` 等），与 prettier 的折行 / 行密度策略存在**结构性冲突**（prettier 倾向在行宽内合并，`@stylistic` 倾向拆行）——n-2 两者可共存只因其 ESLint 规则集极简。因此 n-1 的分工是：**`*.{js,mjs,cjs,ts,vue}` 归 ESLint 独占，prettier 只兜 ESLint 不覆盖的文件类型（CSS 等）**，这正是决策 7「兜 ESLint 范围外格式化」的本意
- `web/.prettierrc.json`：`printWidth: 100`、`semi: false`、`singleQuote: true`；CSS 覆盖关闭单引号（`singleQuote: false`）
- `web/.lintstagedrc.json`：`*.{js,mjs,cjs,ts,vue}` → `eslint --fix`；`*.css` → `prettier --write`
- `web/package.json` 增加 scripts：`format`（仅格式化 CSS）、`lint:staged`
- 根 `lefthook.yml` 的 `lint-web` 命令改为 **`root: web` + `pnpm run lint:staged`**（lefthook 在 web/ 目录执行，glob 相对该目录匹配暂存文件——monorepo 官方支持模式）；glob 扩为 `*.{js,ts,mjs,cjs,vue,css}`。server 侧不引入 prettier（ESLint 全覆盖、无样式文件）

### 3.5 e2e 双 webServer（C4 部分）

`e2e/playwright.config.ts` 改为 async config：

- `webServer` 数组：**后端（`pnpm --filter server run start`，探测 `http://localhost:3000/api/health`，`reuseExistingServer: true`，timeout 120s）+ 前端（现状不变）**
- **无库环境兜底（关键设计）**：后端依赖 PostgreSQL，无库环境自动拉起必然超时红屏，违背「未就绪跳过」的既有策略。因此配置期先做**可拉起性探测**（辅助脚本 `e2e/detect-backend.ts`）：
  1. 3000 端口已有服务 → 视为可复用（`reuseExistingServer` 生效，不重复拉起）
  2. 否则解析 `server/.env`（缺省回退 `.env.example` 默认值 `localhost:5432`）探测数据库端口连通性 → 可达才注册后端 webServer
  3. 均不可达 → **不注册后端 webServer**，全链路用例仍由 `tests/后端连通性.spec.ts` 的 `beforeEach` 探测自动跳过（该跳过逻辑保留不动）
- 纯前端用例（首页展示）不依赖后端，两种环境都照常执行

### 3.6 CLAUDE.md 改造（C1，决策 9）

- 新增 **「当前状态」** 章节（置于「最高优先级规则」之后）：带日期的里程碑段落，每完成一个批次追加一条；本批次完成时写入首条
- 规则引用改为 **`@rules/*.md` 导入语法**：`base.md` / `code-style.md` / `testing.md` 三件套随 CLAUDE.md 会话启动即全文注入，正文保留一句最高优先级宣示与文件链接，不再内联重复规则内容
- 正文与工程化现状同步：提交门禁（lint-staged）、前端单测环境（jsdom）、后端全局设施（中间件）、常用命令（`format`）

## 4. 边界与不做清单

1. **不改 HTTP 状态码语义**：n-1 维持「4xx/5xx 真实 HTTP 状态」（区别于 n-2 的恒 200），分段错误码只改 `code` 字段的取值体系
2. **不建模块段位表文件**：首个业务段位随批次四 system 模块登记，本批次只定规则
3. **不引入访问日志落库**：本批次仅控制台日志（Nest Logger）；操作日志/登录日志落库是批次五范围
4. **e2e 不改 workers/parallel 策略**：无登录会话态，维持 `fullyParallel`；批次四引入认证后再对齐 n-2 的 `workers: 1` 约束
5. **server 不引入 prettier**：ESLint 已全覆盖后端格式

## 5. 验收标准

1. `pnpm check` 全绿（含改造后的存量单测与后端 e2e）
2. `pnpm test:e2e:web` 在本机（后端未启动时）自动拉起前后端并全绿；模拟无库环境（数据库端口不可达且 3000 无服务）时全链路用例跳过、纯前端用例照常通过
3. 访问任意 `/api/*` 接口：响应携带 6 个安全响应头；服务端日志输出一行含 method / 路径 / 状态码 / 业务 code / 耗时的访问日志
4. 错误码契约抽查：`BusinessError` 默认抛错返回 `code: 999`；未知异常返回 `code: 500`；404 / 401 / DTO 校验失败的 code 数值与改造前一致
5. 工具分工无冲突：`eslint --fix` 与 `prettier --write`（仅 CSS）互不触碰对方领域；`web/` 下暂存 `.css` 文件提交时自动被 prettier 格式化
6. 文档同步：《统一响应与异常处理设计》《架构设计》、ADR-002 变更记录、规划批次一回填、CLAUDE.md「当前状态」、docs/README 索引更新
