## 1. 需求背景

批次四交付了认证授权 RBAC 的后端全量接口与前端登录链路，但用户 / 角色管理页移交本期，系统管理域也只有用户 / 角色两张业务表。企业级底座的系统管理还需补齐：**字典**（状态类枚举统一出处）、**参数**（初始口令等配置值表驱动）、**部门与岗位**（组织形态）、**操作日志与登录日志**（审计追溯），以及支撑日志异步入库的**异步任务封装**（B8）。

n-2 已沉淀完整设计（表结构 / 级联规则 / AOP 日志 / 异步线程池），本批次按吸收原则翻译：语义决策平移、实现按 n-1 技术栈与既有契约改写；前端管理页结构照搬、视觉沿用批次三「青碧卡片浮起」token 体系。

## 3. 方案设计

### 3.1 数据模型（八新表 + 加列 + 种子）

**六张业务表继承 `BaseEntity`**（uuid 主键 + 审计列 + 软删，蛇形命名，部分唯一索引 `WHERE deleted_at IS NULL`）：

| 实体 | 表 | 列定义 | 索引 |
| --- | --- | --- | --- |
| `DeptEntity` | `system_dept` | name varchar(50)；parentId uuid **null = 根**；sort int 0；phone varchar(20) null；email varchar(50) null；status boolean true | idx(parent_id) |
| `PostEntity` | `system_post` | code varchar(50)；name varchar(50)；sort int 0；status boolean true | uk(code) partial |
| `DictTypeEntity` | `system_dict_type` | name varchar(50)；type varchar(100)；status boolean true；remark varchar(500) null | uk(type) partial |
| `DictDataEntity` | `system_dict_data` | dictType varchar(100)；sort int 0；label varchar(100)；dictValue varchar(100)；status boolean true；colorType varchar(20) null；remark varchar(500) null | idx(dict_type) |
| `ConfigEntity` | `system_config` | category varchar(50)；name varchar(100)；configKey varchar(100)；configValue varchar(500)；visible boolean true；remark varchar(500) null | uk(config_key) partial |
| `UserEntity`（ALTER） | `system_users` | **新增 deptId uuid null**（逻辑外键） | idx(dept_id) |

**三张不继承 BaseEntity**（与 n-2 同款决策：流水只增不改，无审计无软删，物理删除）：

| 实体 | 表 | 列定义 | 索引 |
| --- | --- | --- | --- |
| `UserPostEntity` | `system_user_post` | id；userId；postId；createdAt（`@CreateDateColumn`）——纯关联值对象，照 `user-role.entity.ts` 形态 | uk(user_id, post_id) |
| `OperateLogEntity` | `system_operate_log` | userId uuid null；userName varchar(30) null；module / name varchar(50)；requestMethod varchar(10)；requestUrl varchar(255)；requestParams varchar(2000) null；ip varchar(50) null；userAgent varchar(500) null；startTime timestamptz；durationMs int；resultCode int；resultMsg varchar(500) null；createTime（`@CreateDateColumn`） | idx(user_id)、idx(create_time) |
| `LoginLogEntity` | `system_login_log` | logType smallint（10 登录 / 20 登出）；userId uuid null（失败可空）；username varchar(30)；ip / userAgent；resultCode int；resultMsg varchar(500) null；loginTime timestamptz；createTime（`@CreateDateColumn`） | idx(username)、idx(login_time) |

与 n-2 的翻译差异：

| n-2 形态 | n-1 形态 | 理由 |
| --- | --- | --- |
| 雪花 BIGINT 主键、parent_id = 0 表示根 | uuid 主键、**parentId = null 表示根** | uuid 域没有 0；服务层防环逻辑同步适配 |
| SMALLINT 0/1 布尔与状态 | PG 原生 boolean | 批次二建表规约（PG 优先） |
| TIMESTAMP 无时区 | timestamptz | 同上 |
| `system_config` 表名 | 表名不变、服务命名 **`SystemConfigService`** | 避开 `@nestjs/config` 的 `ConfigService` 同名混用 |
| 日志表 BaseDO 简化版（仍带 updater） | 不继承 BaseEntity，仅 createTime | 流水只增不改；不触发 `AuditSubscriber`，**异步入库无 AsyncLocalStorage 依赖**（队列执行时已脱离请求上下文） |

**种子迁移**（手写 `SystemExtensionSeed`，id 常量入 `system.constants.ts` 与代码同源）：

- 部门 2 行：根部门「n-1 科技有限公司」（parent null）+ 研发部（parent = 根）；`admin` 用户 UPDATE 挂根部门
- 岗位 3 行：ceo 董事长 / se 研发工程师 / hr 人力资源
- 字典类型 1 行 `common_status` 通用状态；数据 2 行：**dictValue 'true'（启用，success）/ 'false'（停用，danger）**——boolean 适配见 §3.9
- 参数 1 行：`system.user.init-password` = admin123（visible true）
- DDL 经 `migration:generate` 从实体派生，down 按依赖逆序（先置 users.dept_id null 再删表）

### 3.3 异步任务队列（B8）

n-2 形态是 Spring `ThreadPoolTaskExecutor` + `CallerRunsPolicy` 反压（core 4 / queue 200 / 优雅关停 30s）。Node 单线程无线程池概念，翻译为 **FIFO 队列 + 未完成任务数上限的微任务调度器**（`common/async/async-task-queue.ts`，零依赖）：

- 构造参数：`maxConcurrency = 4`、`maxQueueSize = 200`、`drainTimeoutMs = 5000`（首个消费方只有日志入库，单条 insert 毫秒级，排空上限较 n-2 的 30s 缩短；参数化留待第二个消费方出现）
- `submit(task)`：fire-and-forget **永不向调用方抛错**；队列满 → **不排队当场异步执行**（CallerRuns 语义翻译：用当前请求的响应时间吸收背压）；已关停 → warn + 丢弃
- `drain(timeout)`：排空等待，优雅关停与测试共用；`onApplicationShutdown()` 拒新单 + drain（`main.ts` 补 `app.enableShutdownHooks()`）
- 任务异常逐条 `.catch` 仅 `logger.warn`（DB 故障时不刷屏、不反噬业务）
- **纪律**：任务闭包只持纯数据（组装完的实体），不得在任务体内读 `requestContext`——日志表不继承 BaseEntity，无审计填充需求，天然满足
- 装配：provider 注册于 SystemModule（@Global）并导出——AuthService 与根作用域的 OperateLogInterceptor 均可注入（JwtAuthGuard 注入 AuthService 的同款先例）

### 3.4 操作日志（@OperateLog + 拦截器）

**装饰器**（`common/decorators/operate-log.decorator.ts`，纯 SetMetadata 零依赖，批次六起所有业务模块通用的横切标注）：`@OperateLog(module, name)`，METHOD / TYPE 双目标、方法级优先（沿用 `RequirePermissions` 形态）。

**拦截器**（`modules/system/operate-log/operate-log.interceptor.ts`——需注入本域 service 与队列，放 common 会反向依赖业务模块，参照 JwtAuthGuard 依赖 AuthService 故入 system 的先例）：

1. **注册顺序**：`app.module.ts` 中排在 `TransformInterceptor` **之后**（APP_INTERCEPTOR 顺序即洋葱外内序）——OperateLog 为内层、贴近 handler，等价 n-2 AOP 环绕切面位置
2. **无注解短路**：reflector 无 metadata 直接放行、不触达任何依赖——存量接口与 e2e 零影响（`@Public` 同款短路纪律）
3. **结果码取值不读 `request.apiCode`**（该回填位只服务访问日志中间件）：成功路径 Controller 返回裸业务数据按契约 code 恒 0；失败路径 `catchError` 从异常对象取——`BusinessError.code` / `HttpException.getStatus()`（通用段数值 = HTTP 码）/ 其他 500——两条路径同源、可单测
4. **上下文在请求线程内同步取完再异步入库**（n-2 纪律平移）：`request['user']`（复用 `REQUEST_USER_KEY`）、`getClientIp`（X-Forwarded-For 逐跳取首个非 unknown，回退 `socket.remoteAddress`）、UA、method / originalUrl
5. **参数序列化**：`{ body, query, params }` 三合一 JSON 序列化，失败降级 `util.inspect`；**键名为 password 的字段掩敏 `'******'`**（n-2 未掩敏，属安全改进、留痕）；截断 2000 对齐列宽，resultMsg 截断 500
6. **组装失败仅 warn 不反噬业务**；入库经 AsyncTaskQueue
7. **打样**：UserController 五处写接口（创建 / 更新 / 删除 / 重置密码 / 分配角色）标 `@OperateLog('用户管理', '...')`，角色域与批次六模块照抄

### 3.5 登录日志与在线用户形态

**埋点**（`AuthService`，`recordLoginLog` 私有方法统一组装 → 队列入库，任何失败仅 warn 不断阻断登录）：

| 路径 | logType | userId | result |
| --- | --- | --- | --- |
| 登录失败（用户不存在 / 口令错同码） | 10 | null | `AUTH_LOGIN_FAILED` |
| 账号停用 | 10 | 用户 id | `AUTH_LOGIN_DISABLED` |
| 登录成功 | 10 | 用户 id | 0 |
| 登出（Guard 已挂 user，无 n-2 的时序问题） | 20 | 用户 id | 0 |

`AuthController` 的 login / logout 注入 `@Req()` 提取 `{ ip, userAgent }` 传 service（新增 `common/utils/client-info.ts` 工具）。

**在线用户形态**（ADR-003 能力边界定稿）：**不做会话枚举页与逐 token 踢人**——登录日志页即「最近活跃」视角（logType / username 筛选 + loginTime 倒序）；「踢人」语义由用户管理页**停用**承担（Guard 存在性校验使 token 即时失效）。n-2 的 online 页与 kickout 接口不移植。

### 3.7 字典域

- **类型**：create 唯一校验；update 标识变更时**级联改数据归属**（`DataSource.transaction` 手动事务，不引新依赖）；remove 软删 + **物理删除该 type 下全部数据**（防悬空）
- **数据**：create / update 校验所属类型存在 + **同类型下 dictValue 唯一**（服务层校验，软删行已被过滤天然不占位）；remove 软删
- **统一出口** `GET /system/dict/list-all-simple`（挂 `system:dict:query`）：启用类型全集 + 每类型折叠启用数据 `{ id, name, type, datas: [{ label, value, colorType }] }`——前端 dict store 的唯一数据源
- **无缓存直查库**（零外部依赖纪律；缓存进路线图）

### 3.8 部门、岗位与用户域改造

- **部门防环**：parentId null 放行（根）→ 自环拒绝 → 父存在 → 沿父链上溯深度上限 100（`DEPT_PARENT_ERROR`）；删除约束：有子部门（`DEPT_HAS_CHILD`）/ 挂用户（`DEPT_HAS_USER`）禁删
- **岗位**：code 唯一；删除软删 + **物理清理 `system_user_post`** 关联
- **用户域改造**：Create / Update DTO 加 `deptId?`（IsUUID 可选）与 `postIds?`（IsUUID each + ArrayUnique）；存在性校验（dept 单查、post `In` 批量比对数量）；**saveUserPosts 差集增量绑定**（照 assignRoles 样板：现有但目标没有 → delete，目标但现有没有 → insert）；删除时三处物理清理（user_role + user_post）；UserVo 加 `deptId / deptName / postIds`、PageDto 加 deptId 过滤；**分页两笔批量补全**（部门名映射 + 岗位关联分组），避免 leftJoin 软删条件心智
- **权限点清单接口** `GET /system/permission/list`（挂 `system:role:assign-permission`，独立 controller 避开 role 的 `:id` 路由冲突）：返回注册表 `{ code, label }[]`——角色分配弹窗数据源，杜绝前端硬编码权限串

### 3.9 前端

**api 层**（`web/src/api/system/` 九文件：user / role / dept / post / dict / config / operate-log / login-log / permission）：

- 内部 `const { data } = await http.get<T>(...)` 解构后 `return data`——页面层与 n-2 模板零差异
- **GET 必须 `{ params }` 包装**（n-1 是裸 axios 实例）；删除 `http.delete(\`/xxx/delete/${id}\`)`

**dict 三件套**（直搬 n-2 适配）：

- `stores/dict.ts`：模块级 loading Promise 防并发（失败 finally 清 null 可重试）、dictMap 常驻、isLoaded 后不刷新
- `DictTag`：el-tag，label / colorType 由 store 翻译，type 兜底 info——**boolean 值直传天然命中**（`String(true) === 'true'`）
- `DictSelect`：包装 el-select，onMounted ensureLoaded，$attrs 透传

**common_status 的 boolean 适配**（种子 value 'true' / 'false'）：

1. 表格状态列 `<DictTag type="common_status" :value="row.status" />` 零适配
2. 搜索行 DictSelect 提交前 `'true'/'false'` → boolean 转换（utils 小函数）
3. 表单状态字段不用字典，`el-switch` 直绑 boolean（语义对齐，n-2 用字典下拉是因其 0/1 形态）

**路由**（`router/modules/system.ts`，`index.ts` 合并 layoutChildren）：父级 `system`（title 系统管理，icon system，redirect /system/user）+ 8 子路由（user / role / dept / post / dict / config / operate-log / login-log），name PascalCase（SystemUser…），`meta.permission` 挂各域 query 权限，keepAlive true，页面 `defineOptions({ name })` 对齐。**附带小修**：`utils/menu.ts` 的 buildMenuTree 权限过滤后非叶子节点 children 为空则整节点剔除（无任何 system 权限的用户不应看到空分组；menu.spec 增补用例）。

## 4. 边界与不做清单

1. **不做菜单表 / 菜单管理页 / 在线用户会话枚举与逐 token 踢人**（ADR-001 / ADR-003）
2. **不做字典 / 参数缓存**（直查库；缓存进路线图）
3. **不做日志导出 / 批量清空 / 归档策略**（本期分页查询 + 单条删除）
4. **不做操作日志全接口覆盖**（UserController 打样，后续模块照抄）
5. **不引入任何新依赖**（队列 / 拦截器 / 事务均零依赖实现）
6. **不做用户-部门数据权限**（部门仅组织形态，无行级过滤）
7. **不删 configuration.ts 的 user.initPassword**（保留为参数表缺省兜底）
8. **不改存量演示页**（home / demo 的字典化改造不做）
