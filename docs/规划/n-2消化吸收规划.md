# n-2 消化吸收规划

> 兄弟项目 n-2 仓库根：`D:\Others\脚手架\n-x\n-2`（本机同源参考，非本仓库子目录）。
> 本文引用 n-2 内容时均以其仓库根为基准书写路径。

## 1. 需求背景

n-1 当前只有"骨架 + 两个横切设施"：请求签名验证与统一响应/异常处理已完成（代码、文档、测试齐备），但**没有任何业务模块、认证授权、前端布局、数据库迁移与 CI**（README 路线图 5 项基本未动）。

兄弟项目 n-2（同为面向 vibe coding 的企业级全栈底座）已沉淀了大量成熟成果。两者后端异栈（Spring Boot vs NestJS），但**前端技术栈完全相同**（Vue 3 + Element Plus + Pinia + Vite + Vitest），且 n-2 的 `docs/` 设计文档库与工程规则是语言无关资产。本文给出能力差距分析与分批次吸收计划，作为后续若干批次实施的总纲。

**本文只做规划与决策点梳理；每个批次实施前，按"文档先行"规则另写该批次的设计文档。**

## 3. 吸收原则

n-2 内容按移植形态分三档吸收：

| 档位 | 定义 | 纪律 |
| --- | --- | --- |
| **A 前端直接移植** | 技术栈相同，代码近乎 1:1 搬运 | 统一按 n-1 契约适配（错误码、token 形态、命名前缀 `--n2-*` → n-1 自有命名）；**结构照搬、视觉差异化**——布局架构与交互机制保持，视觉层（主色 / 形态质感 / 圆角 / 密度）重新设计，不与 n-2 视觉同质；搬运时同步搬运并改写对应设计文档 |
| **B 后端设计翻译** | Java 生态实现不可搬，但设计决策与数据模型可翻译成 NestJS + TypeORM 形态 | 以 n-2 对应设计文档为底稿改写，不照搬 Java 分层术语；每个翻译决策在本仓库 ADR 或设计文档中留痕 |
| **C 工程化借鉴** | 与语言无关的规则、文档范式、测试组织 | 直接采纳，按 n-1 现状裁剪 |

**反向纪律**：n-1 已有的能力不因吸收而退化——n-1 的签名验证（HMAC-SHA256）、lefthook 双端 lint、MIT 开源 + 头部注释规范均保持不变。

## 5. 不吸收清单

| 内容 | 理由 |
| --- | --- |
| 工作流（Flowable 引擎 + Simple 可视化设计器 + 审批中心十二页） | Java 生态特有，NestJS 无等价物，体量占 n-2 近半——独立产品级投入，不属"消化吸收"；进远期路线图观察 |
| SM4 国密接口加密 | n-1 已有 HMAC-SHA256 签名 + 防重放，覆盖接口防篡改需求；SM4 是信创合规需求，n-1 无此硬约束暂不引入。若将来需要，n-2 的 sm-crypto 前端对等实现 + 固定 IV 跨端一致性测试可直接复用 |
| Sa-Token / MyBatis-Plus / Flyway / Maven 四层结构 / ruoyi 组件 | 框架绑定 Java，只有思想价值（已在 B 档拆出） |
| 多租户、数据权限、代码生成器 | n-2 自身也仅在路线图，无成熟实现可吸收 |
| Hutool → Guava 等工具库选型约定 | Java 特有；n-1 维持现有极简依赖（`@noble/hashes` 等） |
