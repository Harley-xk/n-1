# 批次二：数据层基建设计

> 本文档是 [n-2 消化吸收规划](n-2消化吸收规划.md)「批次二：数据层基建」的实施设计，对应规划条目 **B4 / C7 / 决策 8**。
> 两项前置决策已定稿：主键与逻辑删除见 [ADR-004](../决策/ADR-004-主键与逻辑删除.md)，迁移策略见 [ADR-005](../决策/ADR-005-数据库迁移策略.md)。本文档负责把决策翻译为代码与纪律，并定稿 ADR-005 留给本批次的两个待决点：**迁移操作纪律**与**种子机制形态**。

## 1. 需求背景

n-1 后端目前是「横切设施齐备、数据层空白」的状态：统一响应 / 异常 / 签名 / 访问日志 / 安全响应头已就绪，但 `server/src` 下没有任何实体、没有 `modules/` 目录、没有迁移命令——`DB_SYNC=true` 的 schema 同步是唯一的建表方式（生产不可用）。

批次四（认证授权 RBAC）起每个业务模块都要建表。数据层基建是一切业务表的前置：审计字段自动填充、主键与软删形态、命名策略、建表类型规约、迁移命令与纪律，都必须在第一张业务表出现之前定稿，否则存量表将带着不一致的约定累积。

本批次零业务耦合：不引入任何业务实体与业务表，只交付 `server/src/common/` 数据层公共件 + 迁移机制 + 规约文档。

## 3. 方案设计

### 3.1 审计公共实体 BaseEntity（B4 / ADR-004 实施）

**定位**：所有业务实体的公共基类，继承即获得主键、审计字段与软删能力——「声明即生效」是 TypeORM 形态相对 n-2（插件 + 注解逐字段声明）的核心优势。

`server/src/common/orm/base.entity.ts`：

```ts
export abstract class BaseEntity {
  @PrimaryGeneratedColumn('uuid')
  id: string

  /** 创建人（用户 id，uuid 字符串；系统级操作为 null） */
  @Column({ type: 'uuid', nullable: true })
  creator: string | null

  @CreateDateColumn({ type: 'timestamptz' })
  createTime: Date

  /** 更新人（用户 id，uuid 字符串；系统级操作为 null） */
  @Column({ type: 'uuid', nullable: true })
  updater: string | null

  @UpdateDateColumn({ type: 'timestamptz' })
  updateTime: Date

  @DeleteDateColumn({ type: 'timestamptz' })
  deletedAt: Date | null
}
```

与 n-2 BaseDO 的翻译对照：

| n-2（MyBatis-Plus） | n-1（TypeORM） | 说明 |
| --- | --- | --- |
| `id: Long` + 雪花 `ASSIGN_ID` | `@PrimaryGeneratedColumn('uuid')` | ADR-004：uuid 全链路 string，无精度与中心协调问题 |
| `deleted: Integer`（0/1，`@TableLogic`） | `@DeleteDateColumn`（`deletedAt` 时间戳） | ADR-004：TypeORM 原生软删，查询自动过滤，还能表达删除时刻 |
| `createTime / updateTime` 由 MetaObjectHandler 填充 | `@CreateDateColumn / @UpdateDateColumn` | 框架原生填充，不依赖手写 |
| `creator / updater` 由 MetaObjectHandler 填充 | `EntitySubscriber` 填充（见 §3.3） | 需要请求上下文通路，本批次一并落地 |

**时间列取 `timestamptz` 而非 n-2 的 `TIMESTAMP`（无时区）**——这是有意识的偏离，理由留痕：

1. n-2 选无时区时间戳是 Oracle / 达梦兼容视角（这些库无原生 timestamptz），并需配套「JDBC 会话时区统一」纪律；n-1 决策 8 已收窄为仅主流数据库、优先 PostgreSQL，无此约束
2. 无时区列在跨时区部署下会产生静默偏移（驱动按本地时区解释字面量）；`timestamptz` 全程绝对时刻，配合出口层既有的 `serialize-dates.ts`（Date → 毫秒时间戳）零额外规则
3. BaseEntity 统一显式声明，业务实体不重复决策（规避 `@CreateDateColumn` 默认类型在 PG 下为无时区 timestamp 的坑）

**creator / updater 为逻辑外键**：类型 `uuid` 可空列，**不加物理外键约束**——用户表批次四才出现，且软删场景下物理外键会造成级联困境；引用完整性由应用层保证（规约同步写入 §3.7）。

### 3.2 蛇形命名策略（B4 实施配套）

n-2 规约「列名蛇形小写、不加引号」（PG 折叠小写、天然大小写不敏感）翻译为 TypeORM 命名策略。TypeORM 0.3 起蛇形策略在独立包 `typeorm-naming-strategies` 中，为维持极简依赖，**自写覆写**（继承 `DefaultNamingStrategy`，约 40 行）：

`server/src/common/orm/snake-naming.strategy.ts`，核心是一个 `snakeCase` 转换（处理连续大写与数字边界：`createTime` → `create_time`、`roleId` → `role_id`）。转换函数有边界分支，配同目录 spec 守护。

**装配位置（两处必须一致，否则生成迁移与运行时列名漂移）**：

- 运行时：`app.module.ts` 的 `forRootAsync` 增加 `namingStrategy: new SnakeNamingStrategy()`
- CLI：`data-source.ts` 同样配置

### 3.3 请求上下文与审计填充（B4 实施配套）

`EntitySubscriber` 填充 `creator / updater` 时需要知道「当前操作人」。批次四前没有认证，本批次先把**上下文通路**落地，取不到操作人时填 `null`（系统级操作语义）；批次四的 Guard 解出 JWT 后一行激活。

**请求上下文（AsyncLocalStorage，自写不引依赖）**：`server/src/common/context/request-context.ts`

```ts
const storage = new AsyncLocalStorage<{ userId?: string }>()

export const requestContext = {
  /** 请求中间件调用：开启请求级异步上下文域 */
  run: (store, callback) => storage.run(store, callback),
  /** 取当前操作人 id（无上下文域或未设置时为 undefined） */
  get userId() { return storage.getStore()?.userId },
  /** Guard / 后续环节回填操作人（批次四激活） */
  setUserId: (userId: string) => { const s = storage.getStore(); if (s) s.userId = userId },
}
```

配套 `server/src/common/middleware/request-context.middleware.ts`（薄壳，经 AppModule 注册到全部路由）：为每个请求开启 `requestContext.run({}, () => next())`。ALS 域覆盖后续所有异步链路（Controller → Service → Repository → Subscriber），中间件先于 Guard 运行、store 为可变对象，批次四 Guard 内 `setUserId` 即可写入。

**审计填充订阅器**：`server/src/common/subscribers/audit.subscriber.ts`

```ts
export class AuditSubscriber implements EntitySubscriberInterface {
  listenTo() { return BaseEntity }   // 所有继承 BaseEntity 的实体均触发

  beforeInsert(event: InsertEvent<BaseEntity>) {
    const userId = requestContext.userId ?? null
    event.entity.creator = userId
    event.entity.updater = userId
  }

  beforeUpdate(event: UpdateEvent<BaseEntity>) {
    if (event.entity) event.entity.updater = requestContext.userId ?? null
  }
}
```

注册：`forRootAsync` 增加 `subscribers: [AuditSubscriber]`（与 `APP_*` 全局设施同哲学：装配即全局生效，e2e 自动继承）。

**填充路径纪律（写进架构文档）**——TypeORM 事件只在「实体路径」触发，绕过实体的批量更新不经过订阅器：

| 写路径 | creator / updater 填充 | 约定 |
| --- | --- | --- |
| `repository.save(entity)` / `insert(entity)` | ✅ 自动填充 | **业务代码标准路径** |
| `repository.softRemove(entity)` | ✅ 自动填充 | **软删标准路径**（`deletedAt` + `updater` 都正确） |
| `repository.update(id, partial)` | ❌ 不触发订阅器 | 禁用于需要审计的更新；改走 save |
| `repository.softDelete(id)` / QueryBuilder `.update()` | ❌ 同上 | 慎用，绕过审计填充与 `updateTime` |

### 3.4 迁移体系（C7 / ADR-005 实施）

**独立数据源**：`server/src/data-source.ts` —— 供 TypeORM CLI 使用（`autoLoadEntities` 是 NestJS 特性，CLI 无法感知），与 `app.module.ts` 共用 `configuration.ts` 与命名策略，实体经 glob 指向 `src/modules/**/*.entity.ts`：

```ts
import 'dotenv/config'
import { DataSource } from 'typeorm'
import configuration from './config/configuration'
import { SnakeNamingStrategy } from './common/orm/snake-naming.strategy'

const config = configuration()

export default new DataSource({
  type: config.database.type ?? 'postgres',
  host: config.database.host,
  // ... 端口 / 账号 / 库名同 configuration
  entities: ['src/modules/**/*.entity.ts'],
  migrations: ['src/migrations/*{.ts,.js}'],
  namingStrategy: new SnakeNamingStrategy(),
  // 注意：不配 synchronize —— CLI 永远不隐式改表
})
```

CLI 走 ts-node（依赖已有），需要真实读取 `.env`，故显式声明 `dotenv` 依赖（`@nestjs/config` 传递依赖在 pnpm 严格隔离下不可直接 import）。

**命令挂 pnpm scripts**（`server/package.json`）：

```json
"migration:generate": "typeorm-ts-node-commonjs migration:generate -d src/data-source.ts",
"migration:run": "typeorm-ts-node-commonjs migration:run -d src/data-source.ts",
"migration:revert": "typeorm-ts-node-commonjs migration:revert -d src/data-source.ts"
```

用法（根目录执行）：`pnpm --filter server migration:generate -- src/migrations/<PascalName>`（pnpm 追加参数到脚本尾部）。

**迁移文件**：`server/src/migrations/`，命名 `<时间戳>-<PascalName>.ts`（generate 自动生成）。落在 `src/` 内的理由：`tsconfig.json` 的 `include` 已覆盖、无需新配；`tsconfig.build.json` 不排除——编入 `dist` 后生产可用 `node` 直跑编译产物执行迁移（不依赖 ts-node）。

**基线迁移（ADR-005：存量库首次接入）**：本批次手写 `InitialBaseline` 空迁移（up / down 为空，注释说明语义）：

1. 当前工程尚无业务实体，「存量库」是空库（或含非本工程表）——首个实体出现时（批次四用户表）由 `migration:generate` 生成全量 DDL，即事实基线
2. 空基线的价值：`migrations` 表与版本锚点先落地，后续 generate 的 diff 始终有参照；同时 run / revert 链路即刻可验证，并为后续 AI 生成迁移提供「可模仿的样板」（C3 精神）
3. 真正的存量库接入（已有本工程表的库）纪律：手写基线迁移（结构为空或为当前表状态），`migration:run` 登记版本后接管；**禁止**对存量库直接 generate（会把存量表当作待建差异）

**迁移操作纪律（ADR-005 留给本批次定稿的待决点一）**：

1. `generate` 是「上次快照 + 当前实体」的 diff——生成前**必须核对生成物**（SQL 是否符合预期），生成后先跑 `pnpm check` 再提交
2. **禁止手改生成物后让实体与快照失同步**：改了生成物就必须同步改实体（或反之）；发现失同步的正确动作是 revert 后重新 generate
3. **已执行的迁移只增不改**：任何表结构变更都是新迁移，不修改历史文件（生成物含显式 SQL，git 可 diff、DBA 可读）
4. 手写迁移仅限两类场景：数据变更与种子（admin 初始用户等）；其余一律 generate
5. 生产环境执行方式：`migration:run`（可跑 `dist` 编译产物），或把生成 SQL 交 DBA 审查执行——「同一棵脚本树即交付件」

**种子机制形态（ADR-005 留给本批次定稿的待决点二）**：**采用手写迁移承载种子**（`InitialSeed` 类迁移插入 admin 用户等），不引入独立 seed 命令与种子框架。理由：种子与 schema 版本强相关（列结构变更后种子可能失效），迁移树统一管理可保证执行顺序与幂等位置；首个种子随批次四（admin 用户）出现，本批次不预置空架子。

### 3.5 DB_SYNC 收紧（C7 / ADR-005 实施）

收紧逻辑收敛在 `app.module.ts` 的 `useFactory`（一处决策）：

```ts
const isProduction = configService.get('node.env') === 'production'
const synchronizeRequested = configService.get<boolean>('database.synchronize') // DB_SYNC === 'true'
if (isProduction && synchronizeRequested) {
  logger.warn('生产环境已强制关闭 DB_SYNC（synchronize），表结构变更请使用 migration:run')
}
// ... synchronize: !isProduction && synchronizeRequested
```

`configuration.ts` 补充 `node.env`（`NODE_ENV`）输出；`.env.example` 的 `DB_SYNC` 注释更新为「仅开发便利；生产强制关闭并告警，建表与升级走 `pnpm --filter server migration:run`」。

开发期保留 `DB_SYNC=true` 便利（快速迭代实体），但**迁移接管后建议关闭**——两个建表通道并存时以迁移为准（纪律写入架构文档）。

| 对象 | 层级 | 理由与覆盖点 |

### 3.7 建表类型规约（C5 翻译定稿，决策 8 边界内）

n-2 `rules/sql-compat.md` 的类型规约是为「PG + 国产库」兼容矩阵设计的（布尔用 SMALLINT、时间无时区均为 Oracle 视角妥协）。n-1 收窄为**仅主流数据库、优先 PostgreSQL** 后，按 PG 最佳实践重新定稿（不入 `rules/`，随本设计文档与架构文档承载）：

| 逻辑类型 | TS 侧 | PG 物理类型 | 与 n-2 的差异及理由 |
| --- | --- | --- | --- |
| 主键 | `string` | `uuid` | ADR-004（n-2 为 BIGINT 雪花） |
| 布尔 | `boolean` | `boolean` | **不采纳** SMALLINT 0/1——那是无原生布尔的库的妥协，PG 原生 boolean 语义清晰 |
| 时间 | `Date` | `timestamptz` | **不采纳**无时区 timestamp——理由见 §3.1；出口毫秒时间戳由 serialize-dates 兜底 |
| 状态 / 枚举 | `number` + 常量枚举 | `smallint` | 保留「存码不存串」纪律 |
| 金额 | `number`（配 transformer 如需精度） | `numeric` | 保留：禁 float / double |
| 短文本 | `string` | `varchar(n)` | 保留：显式长度 |
| 长文本 | `string` | `text` | 保留 |
| 外键引用 | `string` | `uuid`（逻辑外键，不加物理约束） | 软删 + 基建节奏下的取舍，见 §3.1 |

**标识符与 SQL 纪律**（自 n-2 翻译，保留）：

1. 列名蛇形小写、**不加引号**（由 `SnakeNamingStrategy` 自动保证）；表名带模块前缀（`system_users` / `system_roles`）
2. 避开保留字（`user` / `order` / `level` 等）——表名有前缀天然规避，列名注意 `desc` / `type` 等加业务前缀
3. SQL 越少越好：优先 Repository API / QueryBuilder 统一构造，**禁止字符串拼接 SQL 片段**；排序 / 过滤字段来自用户输入时必须白名单校验（注入面）
4. 数据库只做存取与简单过滤：计算放应用层；跨库非通用函数（JSONB 运算符等）在 QueryBuilder 中慎用并集中注释
5. **绕过 ORM 的裸 SQL**（`query()` 直跑）仅限性能优化与报表场景，需集中声明与评审

## 4. 边界与不做清单

1. **不建任何业务实体 / 业务表**：本批次零业务耦合，首个实体随批次四用户表出现（届时 generate 出全量 DDL 基线）
2. **不引入异步任务封装**（B8：操作日志异步入库的消费场景在批次五，届时按需评估 worker pool 形态）
3. **不做真库单测基建**（B9/pg-mem）：维持 DataSource 打桩现状；真库验证以浏览器 e2e 与迁移命令手动验收承担
4. **不引入 `typeorm-naming-strategies`、`nestjs-cls` 等第三方包**：蛇形策略与 ALS 上下文均自写（合计约 100 行），维持极简依赖；仅新增 `dotenv` 一项事实依赖（CLI 读 `.env` 所需）
5. **不做 `migrationsRun`（启动时自动跑迁移）**：表结构变更一律显式命令，避免应用启动隐式改库
6. **不做主键 id 显式赋值 / 乐观锁 / 多租户字段**：不在本批次范围
