# 技术架构

> 本文描述 n-1 的整体架构与关键设计决策，随工程演进持续更新。

## 1. 总体架构

n-1 采用 **单仓库（monorepo）+ 前后端分离** 的架构，前后端代码与文档在同一仓库维护，通过 pnpm workspace 统一管理依赖与脚本。

```text
┌─────────────────────────────────────────────────────────┐
│                     浏览器（用户）                         │
└────────────────────────┬────────────────────────────────┘
                         │ HTTP（开发期经 Vite 代理 /api → :3000）
┌────────────────────────▼────────────────────────────────┐
│  web（Vue 3 SPA，:5173）                                 │
│  Vue Router · Pinia · Element Plus · axios(http.ts)      │
└────────────────────────┬────────────────────────────────┘
                         │ RESTful JSON（/api 前缀）
┌────────────────────────▼────────────────────────────────┐
│  server（NestJS 11，:3000）                               │
│  守卫链：签名守卫 → JWT 认证守卫 → 权限守卫                  │
│         → 全局管道（ValidationPipe） → Controller → Service │
│                          │ TypeORM Repository（数据访问）  │
│  横切设施：中间件（请求上下文·安全响应头·访问日志）             │
│            · 全局拦截器 · 异常过滤器                            │
└────────────────────────┬────────────────────────────────┘
                         │ SQL
┌────────────────────────▼────────────────────────────────┐
│  PostgreSQL（独立部署，连接信息由 server/.env 配置）          │
└─────────────────────────────────────────────────────────┘
```

### 端口约定

| 服务 | 端口 | 说明 |
| --- | --- | --- |
| 前端开发服务器 | 5173 | Vite，`/api` 代理至 3000 |
| 后端 API | 3000 | 全局路由前缀 `/api`，Swagger 文档 `/api-docs` |
| PostgreSQL（默认） | 独立部署 | 连接信息经 `server/.env` 配置；可按项目需要切换其他数据库（见「数据访问」） |

## 2. 后端分层设计（server/）

请求处理链路：**HTTP → 横切中间件（请求上下文开启 → 安全响应头注入 → 访问日志计时，`AppModule` 的 `NestModule` 注册）→ 全局守卫链（`APP_GUARD` 数组顺序：签名守卫〔写方法请求签名校验〕→ JWT 认证守卫〔Bearer token 解析 + 用户存在性查库校验，`@Public()` 豁免；通过后回填 `userId` 激活审计上下文〕→ 权限守卫〔`@RequirePermissions` 注解校验，持有任一即放行，缺失抛 403〕）→ 全局管道（参数校验/类型转换）→ Controller → Service → Repository → PostgreSQL**；返回时经全局拦截器（`APP_INTERCEPTOR`）包装为 `{ code, message, data }` 统一结构（含时间字段转毫秒时间戳，业务 code 回填 request 供访问日志输出），任一环节抛出的异常由全局异常过滤器（`APP_FILTER`）归一化处理（同样回填业务 code）。详见[统一响应与异常处理设计](指南/统一响应与异常处理设计.md)、[请求签名验证设计](指南/请求签名验证设计.md)与[权限设计](指南/权限设计.md)。

**横切中间件**（`server/src/common/middleware/`）：

| 中间件 | 职责 |
| --- | --- |
| `RequestContextMiddleware` | 为每个请求开启 AsyncLocalStorage 域（`common/context/request-context.ts`），供审计填充等横切设施读取「当前操作人」；JWT 认证守卫校验通过后回填 `userId`（审计链路已打通） |
| `SecurityHeadersMiddleware` | 所有响应（含 Swagger 文档页）注入 6 个基础防御头（`X-Content-Type-Options` / `X-Frame-Options` / 缓存控制三头 / `Referrer-Policy`）；刻意不加 CSP 与 HSTS（部署层策略，由网关按环境注入） |
| `AccessLogMiddleware` | `/api` 业务接口输出一行访问日志（方法 / 路径 / 状态码 / 业务 code / 耗时），业务 code 经拦截器与异常过滤器回填到 request（`setResponseCode`），文件直通等未回填响应省略 code 段 |

| 层 | 职责 | 约定 |
| --- | --- | --- |
| Controller | 参数接收与校验、调用 Service、返回业务数据 | 不写业务逻辑；返回值由全局拦截器统一包装 |
| Service | 业务逻辑编排 | 可注入 Repository 与其他 Service；业务失败抛 `businessError()`；时间字段返回 `Date` 实例 |
| Entity / Repository | TypeORM 实体建模与数据访问 | 实体随所属业务模块存放；业务实体一律继承 `common/orm/` 的 `BaseEntity`（uuid 主键 + 审计字段 + 软删，见「数据访问」） |

### 模块化组织

业务代码按领域拆分至 `server/src/modules/<领域>/`，每个模块自治（controller、service、entity、dto）。新增模块推荐：

```bash
pnpm --filter server exec nest g resource modules/users
```

### 配置管理

配置链路统一为：**环境变量（.env）→ `src/config/configuration.ts` 汇总 → ConfigService 读取**。

- 环境变量模板见 `server/.env.example`，本地复制为 `.env`（不入库）
- 禁止在业务代码中直接读取 `process.env`
- 请求签名相关配置（`SIGNATURE_ENABLED` / `SIGNATURE_SECRET` / `SIGNATURE_EXPIRE_MS`）汇总为 `signature` 节，详见[请求签名验证设计](指南/请求签名验证设计.md)

### 数据访问

**选型与装配**

- **选型策略**：默认与首选 **PostgreSQL**；**仅承诺主流数据库，不做国产数据库适配**（TypeORM 理论上支持多库切换——在 `server/.env` 修改 `DB_TYPE` 与连接参数并安装对应驱动包——但切换与国产化适配不在本项目保障范围，见 [ADR 决策记录](规划/n-2消化吸收规划.md)决策 8）
- TypeORM 通过 `TypeOrmModule.forRootAsync` 装配，实体在各模块 `forFeature([...])` 注册后自动加载（`autoLoadEntities`）；表 / 列名统一 **蛇形小写**（`common/orm/snake-naming.strategy.ts`，与迁移 CLI 共用同一策略）

**数据层公共基座**（`server/src/common/`，批次二落地）

- **审计公共实体 `BaseEntity`**（`common/orm/base.entity.ts`）：业务实体一律继承，声明即获得——`id`（uuid 主键，接口契约中为 string）、`creator` / `createTime` / `updater` / `updateTime`（审计四字段，时间列 `timestamptz`）、`deletedAt`（TypeORM 原生软删，查询自动过滤已删行）。主键与软删决策见 [ADR-004](决策/ADR-004-主键与逻辑删除.md)
- **审计自动填充**（`common/subscribers/audit.subscriber.ts`）：写入时自动填充 `creator` / `updater`，操作人取自请求上下文（`RequestContextMiddleware` 开启的 AsyncLocalStorage 域）；批次四接 JWT 后由 Guard 回填。**写路径纪律**：`save()` / `softRemove()` 走实体路径自动填充（标准路径）；`update(id, partial)` / `softDelete(id)` / QueryBuilder `.update()` 绕过订阅器，禁用于需要审计的更新，软删统一用 `softRemove()`
- **建表类型规约**（PostgreSQL 优先，完整对照见 [批次二设计文档](规划/批次二-数据层基建设计.md) §3.7）：

| 逻辑类型 | TS 侧 | PG 物理类型 | 说明 |
| --- | --- | --- | --- |
| 主键 / 外键引用 | `string` | `uuid` | 外键为逻辑外键，不加物理约束 |
| 布尔 | `boolean` | `boolean` | 不用 SMALLINT 0/1（无国产库约束，PG 原生布尔） |
| 时间 | `Date` | `timestamptz` | 绝对时刻语义，出口由拦截器转毫秒时间戳 |
| 状态 / 枚举 | `number` + 常量枚举 | `smallint` | 存码不存串 |
| 金额 | `number` | `numeric` | 禁 float / double |
| 短文本 / 长文本 | `string` | `varchar(n)` / `text` | 短文本显式长度 |

- **SQL 纪律**：优先 Repository API / QueryBuilder 统一构造，禁止字符串拼接 SQL 片段；排序 / 过滤字段来自用户输入时必须白名单校验；计算放应用层，数据库只做存取与简单过滤；绕过 ORM 的裸 SQL（`query()`）仅限性能与报表场景，需集中声明

**数据库迁移**（[ADR-005](决策/ADR-005-数据库迁移策略.md)，批次二落地）

- **实体是 schema 的唯一事实源，迁移是自动 diff 的派生物**：`migration:generate` 对比实体与上次迁移快照自动生成变更（TS 文件内含显式 SQL，git 可 diff、DBA 可审）
- 命令（根目录执行）：

| 命令 | 作用 |
| --- | --- |
| `pnpm --filter server migration:generate -- src/migrations/<名称>` | 按实体变更生成迁移（名称 PascalCase） |
| `pnpm --filter server migration:run` | 执行未跑的迁移（建 `migrations` 表记录版本） |
| `pnpm --filter server migration:revert` | 回退最后一个迁移 |

- **迁移纪律**：生成前核对 diff、生成后先过 `pnpm check`；禁止手改生成物后让实体与快照失同步（发现失同步的正确动作是 revert 后重新生成）；**已执行的迁移只增不改**；手写迁移仅限数据变更与种子（admin 初始用户等，种子随迁移承载，不引入独立 seed 框架）
- **存量库接入**：已有本工程表的库先手写空基线迁移登记版本再接管，禁止直接 generate（会把存量表当作待建差异）
- **`DB_SYNC` 收紧**：开发便利开关；生产环境（`NODE_ENV=production`）强制关闭并输出告警，建表与升级一律 `migration:run`。当前基线为 `InitialBaseline`（空迁移，首个业务实体出现时 generate 全量 DDL）

### 接口文档

Swagger 随应用自动生成，访问 `/api-docs`，受环境变量 `SWAGGER_ENABLED` 控制；新接口通过 `@ApiTags` / `@ApiOperation` 等装饰器补充文档元数据。

## 3. 前端架构（web/）

| 目录 | 职责 |
| --- | --- |
| `src/api/` | axios 实例与接口封装；组件内**统一使用 `http` 实例**，不直接创建 axios；请求拦截器自动为写方法注入签名头，`signature.ts` 提供手动签名（非 axios 场景） |
| `src/layouts/default/` | 主布局（顶栏一整条 / 白卡片侧栏 / 标签栏 / 连体白卡片内容区），含默认槽位件与标签操作编排，设计见 [布局与风格设计](前端/布局与风格设计.md) |
| `src/framework/slots/` | 组件槽位注册表：业务以 `registerComponentOverride` 覆盖布局指定槽位，未注册回退默认件 |
| `src/stores/` | Pinia 状态，按业务领域拆分（app 外观 / tags-view 多标签 / counter 示例） |
| `src/router/` | 路由表（静态注册，菜单由 Layout 子路由树生成——ADR-001）与全局守卫；`RouteMeta.title` 自动写入页面标题，`icon` / `hidden` / `keepAlive` / `noTag` 驱动菜单与页签 |
| `src/styles/` | 设计 token（`--n1-*` 明暗双套）+ Element Plus 覆写 + 全局基础样式；业务组件只消费 token，不硬编码色值 |
| `src/utils/` | 工具件：storage 封装、菜单树生成、图标映射、时间戳格式化 |
| `src/views/` | 页面级组件 |
| `src/components/` | 跨页面公共组件（PlaceholderView 占位兜底等） |

- Element Plus 全量引入并启用中文语言包（决策 10：暗色 css-vars 方案依赖全量，不切按需）；暗色模式引入 `theme-chalk/dark/css-vars.css`，三态主题（浅色 / 深色 / 跟随系统）经 app store 切换
- 路由 name 一律 **PascalCase**，与页面 `defineOptions({ name })` 对齐（keep-alive 缓存键契约）；页签粒度 fullPath 一签，缓存跟随页签
- `@` 别名指向 `src/`
- 环境变量以 `VITE_` 为前缀（`.env.development` / `.env.production`），类型声明见 `env.d.ts`
- 单元测试使用 Vitest（配置内嵌 `vite.config.ts`），用例与源码同目录（`*.spec.ts`）

## 4. 测试分层

| 层级 | 工具 | 位置 | 说明 |
| --- | --- | --- | --- |
| 后端单元测试 | Jest | `server/src/**/*.spec.ts` | Service / 工具逻辑，与源码同目录 |
| 前端单元测试 | Vitest（jsdom） | `web/src/**/*.spec.ts` | store / 纯函数 / 组件测试（`@vue/test-utils`），与源码同目录 |
| 后端 API e2e | Jest + supertest | `server/test/` | 无需真实数据库（DataSource 打桩） |
| 浏览器全链路 e2e | Playwright | `e2e/tests/` | 页面 → Vite 代理 → 后端 API；依赖后端就绪的用例自动跳过 |

- 浏览器 e2e 运行：`pnpm test:e2e:web`（条件双 webServer：探测到后端可拉起——3000 已有服务或数据库端口可达——时自动拉起前后端并复用已启动实例；无库环境回退为仅拉起前端，全链路用例自动跳过）
- 浏览器复用本机 Chrome / Edge（channel 方式，无需下载）：默认 Chrome，`E2E_BROWSER=msedge` 切换 Edge；`E2E_BROWSER=chromium` 使用 Playwright 自带内核（需先 `pnpm --filter e2e exec playwright install chromium`）

## 5. 面向 vibe coding 的工程支撑

本框架定位为**企业级项目框架底座**，面向 **vibe coding first** 的 AI 编程范式——用自然语言驱动 AI 编码。框架的一切工程设施，都围绕「让 AI 产出的代码可控、一致、可维护」设计：

1. **规则先行**：`rules/` 沉淀 AI 工作规则（署名、版权、代码风格、完成定义、提交规范），`rules/base.md` 为最高优先级入口，AI 编码前必读
2. **文档先行**：业务开发先在 `docs/` 写设计文档（按模块分目录、中文命名），再写代码，保证 AI 有明确的设计输入
3. **工具强制**：ESLint（`@stylistic` + `import-x`）自动固化代码风格，VS Code 保存即自动修复，`pnpm lint` 一键修复；lefthook 提交门禁在 pre-commit 对暂存文件自动检查、commit-msg 校验提交信息格式，杜绝漏检
4. **自动验收**：Playwright 浏览器测试让 AI 自己写脚本验证自己实现的功能（打开页面 → 交互 → 断言），配合 `pnpm check` 一键自检，形成「编码 → 自检 → 验收」闭环
5. **上下文约定**：`CLAUDE.md` 为 AI 提供项目结构与命令速查，配合 `.vscode/` 一键调试配置与 `.editorconfig` 编辑器一致性，构成完整的 AI 辅助开发工作流
