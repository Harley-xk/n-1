## 背景

n-1 需要一套从代码到服务器的标准化交付链路。已确定的部署前提：

- 使用阿里云效持续集成平台打包，由 git push 触发
- 目标环境为 Ubuntu Linux 服务器独立部署，产物为 Docker 镜像
- 服务器已安装全局 nginx 网关，流量经其转发进容器
- 数据库外置（不进容器、不进镜像）
- 运行配置放在服务器工作目录，以镜像外置方式读取
- 前后端打包为**一个**镜像

待决策的分歧点：镜像内部是否再内置一层 nginx；前端 `.env` 如何进入云效构建环境；镜像如何从云效到达服务器。

## 决策

1. **镜像内置 nginx 作为容器内统一入口**。容器内 nginx 托管前端静态资源，并将 `/api`、`/api-docs` 反代到容器内的 NestJS；服务器全局 nginx 只需转发到一个容器端口（`127.0.0.1:8080 → 容器 80`）。
2. **镜像分发走云效「主机部署」通道**：云效构建机 `docker build` + `docker save` 导出压缩 tar 作为构建产物，由主机部署步骤分发到服务器 `docker load` 后 `docker compose up -d`，不依赖镜像仓库（ACR）。
3. **前端 `.env.production` 保留占位值入库，真实 `VITE_SIGN_SECRET` 经云效流水线环境变量注入**：Vite 构建时进程环境变量优先级高于 `.env` 文件，自动覆盖，无需同步文件。
4. **数据库迁移随容器启动自动执行**：入口脚本等待数据库就绪后运行 `typeorm migration:run -d dist/data-source.js`，再拉起服务（延续 ADR-005「迁移是唯一建表通道」）。

## 理由

- **内置 nginx**：镜像自包含，静态资源与 API 在镜像内同源（与开发期 Vite 代理 `/api` 的形态一致），迁移 / 扩容不依赖宿主机上的文件；服务器全局 nginx 配置保持最简（只认一个 upstream），两级 nginx 的资源开销可忽略。反向方案（静态产物挂载出来由全局 nginx 托管）会让镜像不自包含、全局 nginx 配置耦合部署细节。
- **tar 分发而非 ACR**：单机部署、无多环境分发诉求，省去镜像仓库的开通与维护成本；tar 经云效主机部署通道传输，链路最短。
- **环境变量覆盖而非文件同步**：`VITE_*` 变量本就会打进前端产物，仓库中保留占位值即可让本地构建始终可复现；真实密钥只存在于云效流水线变量与服务器 `server.env` 两处，不进 git 历史。
- **启动即迁移**：外置数据库场景下无需人工登录服务器执行迁移步骤，发布流程一步到位；迁移失败容器即退出并由 `restart: unless-stopped` 重试，故障显性化。

## 影响

- 运行时镜像是 `node + nginx` 双进程单容器，违反「一容器一进程」的教条，属有意取舍：以单镜像交付换取部署拓扑最简，进程管理由入口脚本承担（node 为 PID 1，保留 SIGTERM 优雅关停）。
- 前端签名密钥构建期烧入产物，轮换密钥需重新走流水线构建（后端 `SIGNATURE_SECRET` 运行期可改，但必须与前端一致，实际联动轮换）。
- 服务器侧需一次性初始化 `/opt/n1`（`docker-compose.yml` + `server.env`）与全局 nginx 站点配置，见部署指南。
