# ADR-003：认证与会话方案

- 状态：已接受
- 日期：2026-09-28
- 关联：[n-2 消化吸收规划](../规划/n-2消化吸收规划.md)（决策 2 / 4，批次四 / 五实施）；n-2 `docs/架构设计.md` 会话分级设计（对比参考）

## 背景

认证方案的两个待决点：token 传输形态（`Authorization: Bearer` vs n-2 的 tokenName / tokenValue 双字段）；会话状态（无状态 JWT vs n-2 的 `memory | redis` 有状态会话分级——后者支撑在线用户枚举与踢人下线）。

## 决策

1. **token 形态**：`Authorization: Bearer <jwt>`，HTTP 生态惯例，网关 / 代理 / 其他服务可通用校验。
2. **会话方案**：**无状态 JWT + Guard 内用户存在性校验**——权限 Guard 解析 JWT 后校验用户存在且未禁用（查库实现，可加进程内短 TTL 缓存，形态批次四设计定稿），禁用 / 删除用户其 token **即时失效**。
3. **不引入服务端会话存储**（n-2 的 memory | redis 分级与对应 DAO 不采纳）；签名防重放 nonce store 维持现有内存实现。
4. **能力边界**：不做精确在线会话枚举与逐 token 踢人——"在线用户"以登录 / 访问日志的**最近活跃视角**呈现，"踢人"语义由**禁用用户**承担（token 即时失效）。

## 理由

1. **单实例零外部依赖**：不引入 Redis 即可获得完整认证能力，与底座"开箱即用"匹配。
2. **存在性校验以极小成本覆盖最常见失效需求**：员工离职、账号封禁等场景即时生效，而这类场景正是"踢人"的主要真实诉求。
3. **水平扩展友好**：JWT 天然无状态，多实例部署无需会话同步。

## 影响

- 批次四实现指引：登录 / 鉴权 / 权限 Guard 按此设计。
- 批次五"在线用户"功能形态调整（见规划批次五）。
- 演进出路：多实例部署且出现精细 token 撤销需求时，再引入 token 版本号或撤销列表，届时另立 ADR。
