# ADR-003：认证与会话方案

- 状态：已接受
- 日期：2026-09-28
- 关联：[权限设计](../指南/权限设计.md)

## 背景

认证方案的两个待决点：token 传输形态（`Authorization: Bearer` 头 vs 自定义 tokenName / tokenValue 双字段）；会话状态（无状态 JWT vs 服务端有状态会话分级〔memory | redis〕——后者支撑在线用户枚举与踢人下线）。

## 决策

1. **token 形态**：`Authorization: Bearer <jwt>`，HTTP 生态惯例，网关 / 代理 / 其他服务可通用校验。
2. **会话方案**：**无状态 JWT + Guard 内用户存在性校验**——权限 Guard 解析 JWT 后校验用户存在且未禁用（查库实现，可加进程内短 TTL 缓存），禁用 / 删除用户其 token **即时失效**。
3. **不引入服务端会话存储**；签名防重放 nonce store 维持现有内存实现。
4. **能力边界**：不做精确在线会话枚举与逐 token 踢人——"在线用户"以登录 / 访问日志的**最近活跃视角**呈现，"踢人"语义由**禁用用户**承担（token 即时失效）。

## 理由

1. **单实例零外部依赖**：不引入 Redis 即可获得完整认证能力，与底座"开箱即用"匹配。
2. **存在性校验以极小成本覆盖最常见失效需求**：员工离职、账号封禁等场景即时生效，而这类场景正是"踢人"的主要真实诉求。
3. **水平扩展友好**：JWT 天然无状态，多实例部署无需会话同步。

## 影响

- 实现载体：system 模块 auth / JwtAuthGuard / PermissionsGuard 按此设计。
- "在线用户"以登录 / 访问日志的最近活跃视角呈现（见决策 4）。
- 演进出路：多实例部署且出现精细 token 撤销需求时，再引入 token 版本号或撤销列表，届时另立 ADR。

## 实施定稿（2026-09-28）

- **存在性校验形态**：**逐请求查库**（`getActiveUserById`：`findOne` + `status` 判定）——禁用 / 删除即时失效语义最纯粹，无缓存一致性问题；进程内短 TTL 缓存留作性能优化的后手（届时再评估），本期不做。
- **token 有效期**：**8h**（`JWT_EXPIRES` 环境变量可调，默认 `8h`），payload 只放 `{ sub, username }` 身份标识——角色与权限逐请求现查，变更 / 回收 / 禁用即时生效，不塞 token。
- **依赖**：`@nestjs/jwt` 锁定 **11.x**（12 为 ESM-only 包，Jest CJS 模块系统无法解析；11.x API 一致）+ `bcryptjs`（纯 JS 零原生依赖，`$2a$` 散列与 Spring BCryptPasswordEncoder 互验）。
- **Guard 链**（`APP_GUARD` 数组顺序）：`SignatureGuard → JwtAuthGuard → PermissionsGuard`；`@Public()` 豁免 JWT（登录接口叠加 `@SkipSignature()` 双豁免）。
- **审计打通**：JwtAuthGuard 校验通过后 `requestContext.setUserId(userId)` 一行激活 ALS 审计填充链路。
- **登录防枚举**：用户不存在与口令错误同码同文案（`100000000`「登录账号或密码不正确」）。
