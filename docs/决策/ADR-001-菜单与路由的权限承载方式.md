# ADR-001：菜单与路由的权限承载方式

- 状态：已接受
- 日期：2026-09-28
- 关联：[n-2 消化吸收规划](../规划/n-2消化吸收规划.md)（批次四 / 五）；n-2 `docs/权限设计.md`（对比参考，仓库根 `D:\Others\脚手架\n-x\n-2`）

## 背景

认证授权（RBAC）落地前必须回答：**"页面有哪些、怎么组织"这个知识放在哪里**。两种候选方案：

- **方案一：菜单落库（后台配置）**——n-2 / 若依系传统形态。菜单表 + 菜单管理页，角色-菜单分配决定页面可见性；前端登录后拉取菜单，经 `import.meta.glob` 字符串映射组件并动态 `addRoute`。优点是运行期可调菜单（名称 / 图标 / 排序 / 显隐）不发版。
- **方案二：代码静态路由 + 权限过滤**——路由表完整定义在代码（按模块拆文件），`meta` 携带权限标识；侧栏菜单由「过滤掉 hidden 与无权限项后的路由树」渲染生成。

## 决策

采用**方案二：代码静态路由 + 权限动态过滤生成菜单**。

1. **菜单不是独立数据，是路由的投影**：路由按模块拆文件静态注册（`router/modules/<模块>.ts`），`RouteMeta` 扩展 `title / icon / permission / hidden / keepAlive` 等字段；侧栏菜单 = 按权限过滤后的路由树。
2. **权限分配关系照常落库**：用户-角色、角色-权限（权限点）是真正的运行时数据；**不建菜单表、不建角色-菜单分配表**。
3. **访问控制三层**：路由守卫查 `meta.permission`（页面级）→ 组件内 `v-hasPermi`（按钮级）→ 后端权限 Guard 逐接口校验（**真正的安全边界**，前端菜单只是显示层）。
4. **预留窄扩展后手**：个别项目如需运营期调整显示属性，允许"按路由 name 为 key 的展示属性覆盖"（仅 title / icon / order / hidden 四项，不动结构与权限）——结构在代码、展示可覆盖，不回退到方案一。

## 理由

1. **契合 vibe coding first 定位**：AI 生成新业务模块 = 路由文件（含权限标识）+ 权限点登记 + 后端模块，单一事实源、git 一致、可静态验证。方案一还需同步生成菜单种子迁移并维护菜单 id 段位，"代码 + 库状态"的二元结构对 AI 生成不友好、失配只能运行时暴露。
2. **n-2 的设计原则同源投票**：n-2 将权限点收敛为代码注册表的理由即"开发期确定的内容严格在代码落实"。菜单结构（有哪些页面、层级如何）同样是开发期确定的知识；n-2 保留菜单落库更多是若依形态惯性与"菜单管理页"作为功能本身的存在。
3. **"改菜单要发版"的代价可接受**：菜单结构变化 ≈ 功能变化，本就要发版；纯改名 / 换图标 / 调排序在企业内部系统中频率很低。持续有此需求的是运营型 SaaS 形态，非底座默认形态。
4. **安全性不降级**：无论哪种方案，访问控制的真边界都在后端接口权限 Guard；静态路由进 bundle 至多暴露页面路径，数据接口逐个校验权限，对企业内部系统不构成攻击面增量。

## 影响

- 前端：路由静态注册，守卫按 `meta.permission` 判定；**不引入** `import.meta.glob` 组件字符串映射与运行时 `addRoute` 拼装（404 兜底路由天然最后注册）。
- 数据模型：相比 n-2 少菜单表、角色-菜单表两张表，无菜单种子迁移。
- 系统管理模块：不做菜单管理页；角色分配交互只操作权限点集合。
- 文档复用：以 n-2《权限设计》为底稿改写时，剔除菜单表、菜单/权限合并树分配、菜单 id 段位等章节。
- 测试：e2e 不依赖菜单种子数据。
