## 背景

ADR-006 确定的部署前提不变（云效 CI、Ubuntu 单机独立部署、全局 nginx 转发、外置数据库、配置外置、前后端一体交付）。但其 docker 单镜像方案在镜像分发环节连续受阻：

- 云效官方「镜像构建并推送」步骤与推送 registry 一体化，**无法只构建产出 tar 文件**；「执行命令」步骤实测无 docker daemon
- ACR 个人版对企业实名账号关闭（官方文档：个人版仅限个人用户），企业版超预算
- 剩余路径各自引入外部依赖：kaniko（镜像源国内可得性 + Dockerfile 兼容性实测成本）、服务器自建 registry（常驻服务 + 公网端点 + TLS）、自托管构建机（构建占用服务器资源）

同时重新审视部署拓扑：单镜像方案中「镜像内 nginx」承担的静态托管与 API 反代，与服务器上已有的全局 nginx 职责重复——镜像自包含的可迁移价值在**固定单机**场景中收益极小。而云效最成熟的能力组合（构建产物上传 → 主机部署）天然面向**文件形态产物**。

## 决策

1. 交付主形态为**发布包**（tar.gz）：`web-dist`（前端产物）+ `server`（后端 dist 与自包含生产依赖）+ `release-info`（版本信息），由 `scripts/build-release.sh` 在构建机产出
2. 服务器以 **systemd**（`n1.service`）守护 `node dist/main.js`，`EnvironmentFile` 读取外置配置 `/opt/n1/server.env`
3. **全局 nginx 直接承担流量分流**：静态资源 `root /opt/n1/web-dist`（SPA 回退），`/api`、`/api-docs` 反代 `127.0.0.1:3000`——交付产物内无 nginx
4. **服务器不维护历史版本**：`deploy/release.sh` 覆盖式发布（暂存目录解包 → `rsync --delete` 覆盖 → 数据库迁移 → `systemctl restart` → 健康探测）；回滚依赖云效重发历史构建产物（或 revert 后重跑流水线）
5. 发布包构建依赖 `pnpm deploy --prod --legacy` 提取 server 自包含生产依赖（symlink 相对闭环，不依赖 workspace 根），构建过程不影响本地开发环境

## 理由

- **零中间设施**：无 registry、无 docker daemon、无 kaniko 镜像源、无自托管构建机——CI 与服务器两侧全部是平台原生能力，运维面最小
- **形态最贴合**：「前后端一体」由一个 tar 包满足；「配置外置」由 systemd `EnvironmentFile` 原生满足；「全局 nginx 转发」升级为「全局 nginx 分流」反而消除了 docker 方案的两级 nginx
- **平台一致性可控**：云效构建机与服务器同为 linux x64；server 生产依赖经审查全部为纯 JS（bcryptjs / pg / typeorm 无原生模块），node 大版本锁定 22 即可
- **回滚代价权衡**：云效历史产物重发约几分钟完成；服务器本地版本管理只额外买到秒级回滚与 CI 故障兜底，代价是磁盘占用与脚本复杂度——单机低频发布场景不值

## 影响

- 服务器需一次性安装 node 22（nodesource 源）；运行期组件仅 systemd（系统自带）+ 全局 nginx（已有）
- 失去容器级环境隔离：操作系统 / node 版本漂移可能引入「构建机正常、服务器异常」（风险由「同 OS 同架构 + 纯 JS 依赖 + 大版本锁定」收敛）
- 发布存在秒级服务中断（`systemctl restart`），与 docker `compose up -d` 同量级，可接受
- docker 资产（Dockerfile、docker/、deploy/ 的 docker 相关文件与《Docker 打包与部署指南》）保留为备选，未来多机 / 容器化演进时启用
